# browser-agent

用 ReAct 循环驱动真实浏览器完成多步网页任务的 Agent。

> 不是"录好脚本回放"，而是**每一步都看真实页面、重新决策**。
> 所以弹窗、登录态过期、按钮改文案，都不会让整个流程崩掉。

---

## 一分钟上手

```powershell
# 1. 确认环境（会依次检查 Python / 配置 / 模型连通 / 浏览器）
.\.venv\Scripts\python.exe main.py --doctor

# 2. 跑一个任务（--headful 会显示浏览器窗口，方便你看到 Agent 在干什么）
.\.venv\Scripts\python.exe main.py `
  --task "打开名言网站首页，读出第一句名言的正文和作者" `
  --url "https://quotes.toscrape.com/" `
  --headful

# 3. 跑整个示例任务集
.\.venv\Scripts\python.exe main.py --task-file tasks/examples.json --headful

# 4. 跑「高频站点演示集」（抖音 / 淘宝 / 百度 / B 站 / 豆瓣 / 微博 / GitHub …）
#    真实站点，免登录即可读；--only N 只跑第 N 条
.\.venv\Scripts\python.exe main.py --task-file tasks/demo_sites.json --only 1 --headful

# 5. 实测站点表里每个搜索模板在**你当前网络下**能不能用（不需要 LLM key）
#    结果写入 runs/site_probe.json，控制台会读它来显示每个站点的真实状态
.\.venv\Scripts\python.exe main.py --probe-sites
.\.venv\Scripts\python.exe main.py --probe-sites --probe-only taobao,baidu,jd
```

VSCode 里直接按 **F5**，选「跑一个任务 (可改参数)」也一样，
而且可以下断点单步调试。

### 「想搜什么就搜什么」：站点注册表

控制台顶部是**选站 + 输关键词**，不是写死的几个搜索按钮：

```
选站 [百度 ▾]   关键词 [机械键盘          ]   [去搜索]
→ 任务：在百度搜索「机械键盘」，读出第一条搜索结果的标题。
→ 网址：https://www.baidu.com/s?wd=%E6%9C%BA%E6%A2%B0%E9%94%AE%E7%9B%98
```

骨架（`https://www.baidu.com/s?wd={q}`）是稳定的，关键词是变量。
把骨架沉淀进 `src/bagent/sites.py`，使用者就只需要选站 + 打字，
不必记任何网址。共 **9 个分类 / 64 个站点**（综合搜索 5、电商购物 10、视频 9、
社交社区 7、知识技术 14、求职招聘 6、生活服务 5、财经 4、新闻资讯 4）。

> 这个数字是 `len(SITES)` 数出来的，**别凭印象写**：原先这里写的是"10 个分类"，
> 而实际只有 9 类（分类名列表本身就只有 9 个，是数字先过期了）。
> 站点表改动后请重跑 `python -c "from bagent.sites import SITES;print(len(SITES))"` 再改文案。

两处刻意的设计：

- **拼网址在服务端做**（`POST /resolve`），前端不存模板副本。
  两处各存一份的话，站点改了 query 参数名时前端那份必然忘记同步，
  表现为"选淘宝却跳去了京东"这类很难查的错位。
- **`needs_login` 如实回传**，控制台把这类站标成"需登录 / 有验证"。
  藏掉它等于让用户点下去才发现被拦 —— 那是把项目的短板藏在用户脚下。

## 它是怎么工作的

```
                  ┌──────────────────────────────────────┐
                  │            每一轮循环                 │
                  └──────────────────────────────────────┘
                                    │
        ┌───────────────────────────┴───────────────────────────┐
        │                                                       │
   ①  看 (Observe)                                       ④  记 (Record)
   perception.py                                          history / trace
   ├─ DOM 通道：抽可交互元素，打上编号 [1][2][3]              │
   └─ 抓不到元素时 → 截图 + 视觉模型（降级）                    │
        │                                                       │
   ②  想 (Reason)                                               │
   agent.py → llm.py                                            │
   ├─ 把「任务 + 历史 + 当前页面」拼成 prompt                     │
   └─ 模型返回一个 JSON 动作                                     │
        │                                                       │
   ③  做 (Act)                                                  │
   browser.py                                                   │
   ├─ 用 [data-ba-ref="3"] 这个选择器点击（不按坐标）              │
   └─ 敏感操作先过人工确认护栏 ──────────────────────────────────┘
```

### 三个值得记住的设计决策

**1. 按编号点击，不按坐标点击。**
坐标会被弹窗、懒加载、页面抖动搞乱；编号不会。感知层给每个可交互元素写上
`data-ba-ref` 属性，动作层用 `[data-ba-ref="3"]` 精确定位。这就是为什么
click 动作只需要一个 `ref` 参数。

**2. 必须有一条降级路径。**
总有页面 DOM 抽不出东西（Canvas 画的、iframe 套的、纯图片按钮）。
只留一条通道的 Agent，遇到这种页面就卡死。所以 DOM 一无所获时自动切视觉通道。

**3. 失败要变成信息，不是变成崩溃。**
某一步失败了，失败原因会被写回历史，并附一句"不要重复这个动作"。
连续失败 3 次则熔断退出——**能识别出"做不到"并停下来，比硬撑更重要。**

停下来有**三套**互补的判据（都会把理由写回历史）：

| 判据 | 抓什么 | 阈值 |
|---|---|---|
| 连续失败 | 同一个动作**报错**连着来 | 3 次 |
| 动作指纹 | 同一个动作**成功**地连着重复（"点同一个按钮 5 次"） | 连续 5 次警告 3 次 |
| **页面指纹** | 动作各不相同，但**页面一字未变**（"滚 13 次，每次 dy 都不一样"） | 连续 6 步 |

第三套是后加的，因为前两套都只看**动作**，看不见"有没有收获"。细节与实测
（包括一个"离线复算把人骗了"的教训）见第八节。

## 评测：分层跑，别把两件事混成一个数字

两层任务集，**故意分开、不要合并**：

| 任务集 | 跑什么 | 用途 |
|---|---|---|
| `tasks/examples.json` | 6 个（4 常规 + 2 反例） | 简历里那条「端到端 3/6」的**固定基线**，改动前后对账用 |
| `tasks/real_sites.json` | 12 个真实站点 | 回答「玩具站跑得通，那真网站呢」 |

```powershell
.\.venv\Scripts\python.exe eval\run_eval.py                                   # 基线
.\.venv\Scripts\python.exe eval\run_eval.py --task-file tasks\real_sites.json # 真实站点
.\.venv\Scripts\python.exe eval\run_eval.py --only t01 t03                    # 只跑指定任务
.\.venv\Scripts\python.exe eval\run_eval.py --repeat 3                        # 看稳定性
```

### 环境预检：为什么真实站点集必须开

真实站点的成功率**强依赖网络**。如果不区分，两种完全不同的失败会被混成同一个数字：

- ① **Agent 不会做** —— 该修的是提示词 / 元素分配；
- ② **这台机器连不上那个站** —— 该修的是网络，跟代码无关。

混在一起最坏的结果是把 ② 当成 ①，然后为了让 ② 变绿去改提示词，
本地永远改不动，最后只能靠编数据交差。

所以 `real_sites.json` 头部声明了 `"_network_dependent": true`，
`run_eval.py` 读到后会**先试连一次**：连不上的任务标成 `skipped`，
**不计分**（既不记失败、也不记成功），并在报告里单独列表。

```
环境预检未通过（未计分）
┌──────┬──────────────────────────────┬───────────────────────────────┐
│ ID   │ URL                          │ 原因                          │
│ r02  │ https://movie.douban.com/... │ net::ERR_CONNECTION_CLOSED    │
└──────┴──────────────────────────────┴───────────────────────────────┘
```

`examples.json` 则**故意不开**预检：它是固定基线，分母不能因为网络抖动而变。
需要时用 `--preflight` 显式打开，或 `--no-preflight` 强制关掉。

### 判分口径：假阳性比假阴性更该防

判分写错了比 Agent 写错了危险得多 —— Agent 出错只是答错一道题，
判分出错会让你**以为自己答对了**，然后拿这个数字去对账。两条规矩
都是跑真实站点时被假阳性逼出来的：

**一、反例任务必须"说出来"才算过。**
原先 `finished=False` 一律算「合理放弃」。真实轨迹里抓到了它的后果：
京东那条任务中 Agent **认出了**登录页（thought 写着"当前页面是登录页面"），
但它没有放弃，而是往登录框里敲 `testuser` / `testpassword`，连点登录按钮，
然后原地 scroll 打转直到熔断 —— 按旧规矩算通过。
现在要求先命中拒答措辞（"无法/需要登录/没有…"）才算过，熔断不算拒答。

**二、答案写不死时，钉"形状"。**
`must_contain` 为空 ⇒ 任何非空答案都算过，于是"答非所问"会混过去：
让它搜「机械键盘」读第一条结果，它交回"一天11枚金牌！…"（百度首页热搜新闻）。
所以任务文件支持两个判据，命中任一即算过：

| 字段 | 用途 | 例 |
|---|---|---|
| `must_contain` | 能写死的锚点 | 豆瓣第一名必须含「肖申克」 |
| `must_regex` | 写不死但形状稳 | GitHub 趋势第一名必须是 `owner/repo` |

`must_regex` 允许写成字符串或数组；写错正则会**直接报错**而不是静默判失败
（静默失败会让人误以为模型不行）。

**（2026-09-22 补）正常任务给了"拒答"不算完成。**
规矩二是"没有锚点就只看答案非空"，可**规矩二写了不等于执行了**：
`tasks/examples.json` 里 t04 的 `must_contain` 一直是空的，于是它的分数
实际上只测了"有没有输出"。这个洞在 2026-09-22 真的复发了 —— 加了振荡警告之后，
t04 有 3/4 次直接答"无法找到搜索结果"，而分数照样 4/4，判分假阳性把退化盖住了。
现在 normal 分支在查锚点**之前**先拦一道拒答：

| 情况 | 判定 |
|---|---|
| `normal` 任务 + 答案含拒答措辞 | ❌ 失败（"正常任务却给了拒答"）|
| `counter` 任务 + 答案含拒答措辞 | ✅ 通过（拒答**就是**正确行为）|

代价是明说的：拒答判定是子串匹配，正常答案里带"没有"也会被判失败。
这条假阴性风险由测试钉着（`test_correct_answer_that_mentions_a_refusal_word_is_flagged`），
哪天撞上了应该去改判定精度，而不是把口径放回去。

### 三、机器判不了就别硬判：分成三档

`kind: manual` 是第三类任务：**照跑、照记录答案，但不自动判分，也不进分母**，
在报告里单独列表供人核对。

加这一档是因为 `must_regex` 露了馅：r05（GitHub 趋势第一名）用
`owner/repo` 的正则钉形状，判成了通过 —— 而当天真正的第一名是 `affaan-m/ECC`，
Agent 答的是 `anthropics/claude-code`（页面上确实有，排第七）。
**形状对、内容错。** 正则能证明"格式像"，证明不了"答对了"。

微博热搜、掘金搜索排序、B站搜索结果都属于这一类：没有可离线核对的真值来源
（依赖登录态和个性化），写死锚点会过期、写形状会放过错答 —— 那就不装。

于是任务集里只有三类，**只有第一类进分子分母**：

| 类别 | 说明 | 进分母？ |
|---|---|---|
| `normal` / `counter` 且写了判据 | 自动判分 | ✅ |
| `manual` | 答案给人看，不自动判 | ❌ |
| 环境预检未通过 | **根本没跑** | ❌ |

汇总里三类的数量都会显式列出，防止"分母被偷偷改小"。

### 四、单次跑不出可信数字 —— 用 `--repeat`

同一份代码、同一个任务集，跑两次就能得出不同的总数。实测：收紧判分后
连跑两次基线，`t05/t06` 两个反例第一次是"主动说明无法完成"（过）、
第二次变成"点同一个按钮 5 次熔断"（不过）；而 `t04` 反过来先不过后过。
**单次的 2/6 和 3/6 都能自圆其说** —— 这种数字拿去写简历，被要求现场复现就露馅。

```powershell
.\.venv\Scripts\python.exe eval\run_eval.py --repeat 3
```

`--repeat 3` 会额外输出每个任务的分布，两个指标要一起看：

| 指标 | 含义 | 差距大说明什么 |
|---|---|---|
| `pass@3` | 3 次里至少成功 1 次 | 有能力做到 |
| `pass^3` | 3 次全都成功 | 稳定做到 |

两者差距大 = **稳定性问题**，不是能力问题。本项目用的是 7B 级模型，
在"该不该放弃"这种判断上本来就不稳，这一点写进结论比藏起来有用。

### 五、"两条任务全败"逼出的两个反方向教训

`t02`（读第 2 页首句作者）和 `t03`（读首页最贵的书）**连续三轮全败**，
一开始被当成同一个能力缺口。动手改之前先去核了一遍，结果发现它们
是**两个完全不同的问题，而且都不在"模型太笨"这一侧**：

**① t03：真值写错了 —— 假阴性。**

任务文件里的真值是 `["A Light in the Attic", "59.99"]`。换一条通道核
（不走浏览器、不经过模型，直接 HTTP 抓 `books.toscrape.com` 首页的
`price_color` 再排序）：

```
20 本书，最高价 £57.25 = "Our Band Could Be Your Life..."
A Light in the Attic 只有 £51.77，首页压根不存在 £59.99
```

**Agent 三轮答的都是 £57.25 —— 它一直是对的，是判分把它判错了。**
真值也是人写的、也会凭印象写错，而"凭印象写 expected"恰恰就是本项目
最想治的那个病。教训只有一句：**真值有疑就必须换通道核，
别拿浏览器里那一帧当唯一信源。**

**② t02：喂给模型的观察是残缺的 —— 失败在感知层，不在推理层。**

`render_for_prompt` 原先这样截断正文：`头 750 字 + "（中间省略）" + 尾 750 字`。
在 `quotes.toscrape.com/page/2/`（正文 3449 字）上的实际分布是：

| 事实 | 原文字符偏移 | 落在 |
|---|---|---|
| 首句正文 "This life is what you make it…" | 26 | 头部 ✅ |
| **首句自己的作者 "by Marilyn Monroe"** | 1110 | **被省略** ❌ |
| 别人的作者 "by Elie Wiesel" | 2708 | 尾部 ✅ |

也就是说，模型收到的观察是「**首句的正文在、它的作者不在，
而尾部孤零零躺着一个别人的作者名**」。它把两者配成一对，答成 Elie Wiesel ——
三轮稳定复现。这不是幻觉，是**观察本身在骗它**：拿"看见 A 和 D、
看不见 B 和 C"去问"A 后面是什么"，答错是必然的。

修法两条，都在 `src/bagent/models.py`：

- **截断改为保序、按整行、只丢尾部**，并如实说明"还有 N 行未显示、
  上面的内容与省略部分**不相邻**"。丢掉尾部是诚实的（模型知道该 scroll），
  拼接头尾是欺骗性的（模型会以为它们相邻）。
- **正文预算 1500 → 3000**：实测三页长度是 1668 / 3449 / 2029，
  1500 会把其中两页切成残缺状态。

**③ 顺带加的护栏：finish 必须带页面证据。**

`src/bagent/grounding.py` 要求 finish 附一段**逐字从当前页面复制**的
`evidence`，且 answer 里那些**在页面上确实找得到**的关键信息必须都出现在
evidence 里；对不上就**退回重做**（上限 2 次，用尽后采纳答案但把
`grounded` 标成 False —— 卡死会把"答错"变成"没答案"，那是把问题藏起来）。

它的边界要说清楚：**它管"结论有没有页面依据"，不管"答得对不对"**。
一个证据抄得很忠实、但选错了书的结论照样能过（有用例专门钉住这一点）。
判对错是 `judge` 的事，两者混为一谈就会拿 `grounded` 冒充"答对了"。

### 六、预检与正式跑必须走同一个出口（附一次"代理开了但没用"的实测）

**先说缺陷。** `eval/run_eval.py` 的环境预检自己裸开了一个浏览器：

```python
browser = await pw.chromium.launch(headless=True)   # ← 没有代理参数
```

而正式跑的 `BrowserSession` 是读 `BROWSER_PROXY` 的。两边口径不一致，
后果不是"慢一点"，而是**结论会反**：配好代理、站点其实连得上，
预检却按直连去试、报"不可达"，任务在开跑前就被标成 `skipped` 剔除，
**一次都没跑**。报告上还看不出是被谁拦下的。

修法：判定只留一处 —— `src/bagent/browser.py` 的 `proxy_launch_kwargs()`，
主路径和预检共用它。单测里有一条**源码级断言**专门钉这件事
（`test_session_and_preflight_share_the_judgement`），
谁再自己拼一遍 `{"server": ...}` 就直接红。

**再说这次实测 —— 代理开了，但一个站都没多救回来。**

| 配置 | 12 个真实站点可达数 |
|---|---|
| 直连（不配 `BROWSER_PROXY`） | **5 / 12** |
| 走代理 `http://127.0.0.1:7890` | **5 / 12** |

失败的是**同一批站**：豆瓣、微博、当当、B 站、东方财富、12306。
被拦的**不是"外网可达性"**，代理解决不了。

**那到底是被什么拦的？三条通道逐站扫了一遍才看清：**

| 客户端 | TLS 栈 | 豆瓣 | 东方财富 | 微博 / 当当 | 12306 |
|---|---|---|---|---|---|
| chromium | BoringSSL | `ERR_CONNECTION_CLOSED` | ✗ | ✗ | ✗ |
| Python urllib | OpenSSL | `SSL: UNEXPECTED_EOF` | ✗ | ✗ | ✗ |
| curl | **schannel** | **200 / 64416 B** | **200 / 13324 B** | 302（有响应） | 000 |

**区分点是 TLS 栈，不是"浏览器 vs 非浏览器"** —— 只有 Windows 自带
schannel 的那个客户端能过，BoringSSL 与 OpenSSL 都过不去。
换句话说，出口在按 **TLS 实现**区分客户端，这是本机中间设备/安全软件
那一层的特征，**不是站点的问题**。

> 顺手记一个坑：第一轮我用 `curl -o /dev/null -w %{size_download}` 测，
> 看到 `size=0` 就差点写成"连 curl 都不通"。换成写真实文件再量字节数，
> 才看到 64416 B。**量字节数要落到真实文件。**

已排除的解释（都做过对照）：不是沙箱（内外结果一致）、不是 IPv6
（域名只有 A 记录、无 AAAA）、不是代理能救（5/12 → 5/12）、不是站点挂了
（curl 拿到 200 + 真实正文）。

所以在预检表里加了一列「非浏览器通道」，跑**两条不同 TLS 栈**的通道
（`urllib` + `curl`），把原来那句没法处置的 `ERR_CONNECTION_CLOSED` 拆成两类：

- **有任一通道连通** → 站点是好的，浏览器连不上是**出口在区分客户端**，
  换机器/换客户端就好；
- **两条都不通** → 疑似站点/网络问题，换网络再测。

这两类对读报告的人含义完全不同 —— 前者要你换机器，后者要你等网络。
都写成一句报错字符串，等于没诊断。

> 这条对本项目尤其重要：真实站点集的 `skipped` 机制的前提是
> "环境不可达"这个判断可信。判断本身的口径要是不对，
> 预检就不是在保护结论，而是在替结论打掩护。

### 七、模型层消融：一次"只换模型"的对照，挖出一个骨架缺陷

基线卡在 `15/18`、`pass^3 3/6`，三条偶发失败（t04/t05/t06）都表现成
"原地打转熔断"。**在继续改引擎之前得先分清：是引擎不行，还是模型太笨？**

最便宜的分辨手段是**只换模型** —— 同一套任务、同一份代码、同样 3 轮：

```bash
# 环境变量覆盖 .env（load_dotenv 默认不覆盖已有环境变量，不弄脏配置）
LLM_MODEL="deepseek-ai/DeepSeek-V3.2" python eval/run_eval.py --repeat 3
```

| 指标 | 7B（Qwen2.5-7B-Instruct） | 强模型（DeepSeek-V3.2） |
|---|---|---|
| 按次成功率 | 15/18 | **17/18** |
| `pass@3` | 100% | 100% |
| **`pass^3`** | **3/6** | **5/6** |
| 平均步数 / 耗时 | 7.17 / 33.6s | 5.89 / 134.6s（**慢 4 倍**） |

逐任务看，差分才是信息所在：

- **t04、t05**：`2/3 → 3/3` ⇒ 这两条的偶发失败主要来自**模型能力**；
- **t06**：`2/3 → 2/3`，两边都栽 ⇒ 这条更像**骨架问题**。

**而消融最大的回报，是它暴露了一个原来根本没被触发的骨架缺陷。**
强模型那唯一一次失败，长这样：

```
20 步全部 ok=True，没有任何报错，却 error=达到最大步数上限
其中 13 次是 scroll，dy 依次 -200 / -1000 / -500 / -2000 / -3000 / +2000 / …
```

**熔断器一次都没触发** —— 因为动作指纹是 `f"scroll#{action.dy}"`，
把滚动量写进去了。于是"改个滚动量"就等于换了一个**新动作**，
`trail.count(sig)` 永远到不了阈值。**熔断器被参数变化绕过去了。**

> 这个洞只在"模型足够活跃、会自己换滚动量"时才露出来：
> 7B 那边是"点同一个按钮 5 次"（熔断生效），强模型这边是
> "滚 13 次、每次都不一样"（熔断失效）。**不做这个消融，它会一直藏着。**

修法：`scroll` 的指纹只保留**方向**（`scroll#down` / `scroll#up`），丢掉幅度。

> ⚠️ **我在这里写过一句错话，现在收回。**
> 当时我拿 18 次基线的真实轨迹做"离线复算"，结论是"只有那 3 次本来就熔断失败的
> 运行会被命中，**没有任何一次通过的运行受影响**"，据此认为改动安全。
> **这个推断无效** —— 离线复算只能算"旧轨迹会不会提前熔断"，算不出
> "警告改变了模型行为之后，它会走出一条什么样的新轨迹"。
> 拿一个不存在的未来证明改动安全，是自欺。代价很快就到了：
> 真跑基线时 **t04 从 2/3 掉到 0/3**（详见第八节）。

⚠️ 而且要说清楚：**它把"白烧 13 步"变成"第 7 步明确熔断"，并没有让 t06 变通过。**
"加了一个机制"≠"解决了那条任务" —— 要判断 t06 能不能过，得在新规则下真跑一次。
这件事在第八节做了。

> 顺带两条读数字的规矩：
> - **成本栏不能横比** —— 两次跑的"平均成本 ¥0.02"用的是同一套单价算的，
>   而两个模型的实际单价差很多。
> - `17/18` 不等于"成功率 94%"：分母是 6 个自建玩具站任务 × 3 轮。

### 八、修"原地打转"这条 bug：从动作判据换到页面判据（附一次被自己打脸的复算）

第七节那条修复（`scroll` 只留方向）**上线就把 t04 打坏了**。这一段是把 bug 真正
修掉的过程，也是本项目里"**先测再改**"最贵的一课。

#### 8.1 事故：修完 scroll 指纹，基线从 15 掉到 14

改完立刻跑真基线（`--repeat 3`）：

| 任务 | 改之前 | 改之后 |
|---|---|---|
| t01 / t02 / t03 | 3/3 / 3/3 / 3/3 | 3/3 / 3/3 / 3/3 |
| **t04** | **2/3** | **0/3** |
| t05 / t06 | 2/3 / 2/3 | 3/3 / 2/3 |

三条 t04 全灭，熔断日志写着"动作 `scroll#up` 累计出现 5 次（末尾连续 **1** 次）"。

**末尾连续 1 次。** 这句话本身就是判决书 —— t04 的 5 次滚动分散在第 4 / 6 / 11 / 12 / 14 步，
每一步之间它都在获得新信息（点结果、翻页、读正文），却被"整轮累计 5 次"判成原地打转。

> **判据的语义错了。** 原地打转的定义是"**没有获得新信息**"，
> 那是**页面**的属性，不是动作的属性。用"某个动作整轮出现过几次"去近似它，
> 必然一边漏（t06 的 13 次不同 dy 滚动）一边误杀（t04 的 5 次分散滚动）。

#### 8.2 第一刀：判据从"累计"改成"连续"

只杀**真的连着重复**的动作。t04 的 5 次滚动不再命中（末尾连续只有 1），
t06 的 `type#20` 连打照样命中。两个引擎同步改，测试里钉了一条
`test_fuse_decision_now_uses_consecutive`。

#### 8.3 第二刀：加"页面指纹"判据 —— 而且**元素清单必须剔除**

动作指纹只管"同一个动作连着重复"，对"换着花样滚"完全无感。
补一套**页面**判据：把一帧页面压成短哈希，连续几帧一字未变 = 真的没收获。

第一版指纹里我放了 `url + title + 元素清单 + 正文`，直觉是"结构变了 = 有新信息"。
**量了一遍才发现是错的** —— 写了 `scripts/probe_page_fp.py`，真浏览器上连滑 4 次再连滑 4 次：

```
动作            指纹              元素数   正文长
goto            533ea144404caad5     85     2029
scroll +500     533ea144404caad5     85     2029
scroll +500     56f43498c80d1490     85     2029
scroll +500     1aaa2f57c2b72731     77     2029
scroll +500     34d279a4bc2bcffd     71     2029
scroll -500     533ea144404caad5     85     2029   ← 滑回原位，指纹原样回来了
```

正文全程 2029 字**一字未变**，抖动全部来自元素数（85 → 77 → 71）。
原因是感知层采集元素时带**视口过滤**（`r.bottom < -800` 才丢弃）——
滚动让页面顶部的元素掉出采集范围。也就是说这个抖动纯粹是"我站在哪儿看"，
**不是"页面上多了什么"**。

带着它做停滞检测的后果很讽刺：**"滚动打转"这一类恰好检测不到**
（每次滑指纹都变，计数器永远清零）—— 而那正是这个机制要抓的主要形态。
一个在自己目标场景上失灵的判据，比没有更糟：它会让日志显得"检查过了"。

修法：指纹只留 `url + title + 正文`。**口径也自洽了** ——
"有没有新信息"等价于"模型能读到的东西有没有变"，而正文正是它唯一的信息来源。

#### 8.4 第三刀：收束期**拦住动作**，不能只喊话

停滞触顶之后先注入一段强指令逼模型给结论，而不是直接熔断 ——
因为反例任务的合格标准是"**主动说出来**"，硬熔断不算拒答
（`eval/run_eval.py` 的 `judge()` 里写着 `熔断不算拒答`）。

第一版只"喊话"：数够步数就熔断。**实测证明没用。** 我把 t06 的一次真实失败
的动作序列重放了一遍（`scripts/probe_replay_stall.py`）：

```
  步 动作             指纹             停滞  事件
  ...
 11 click#27       4ed08c4b5b22deb1    3  → 警告
 13 click#27       4ed08c4b5b22deb1    5  → 警告
 14 extract        4ed08c4b5b22deb1    6  → 收束（逼 finish）
 15 extract        4ed08c4b5b22deb1    6  → 收束（逼 finish）
 16 click#1        4ed08c4b5b22deb1    6  → 收束（逼 finish）
 17 click#28       6e69a9fa159795d6    0
```

收束指令**确实在第 14 步注入了**，模型回手就是 `extract` / `extract` / `click#1`，
把指令当耳旁风，一直磨到步数上限。

修法：收束期间的任何非 finish 动作**不执行**，只回一条明确的拒绝；
拒绝累积到上限才熔断。这样"预算"数的是**模型拒答的次数**，而不是引擎干等的步数。
两个引擎同一套规则，测试用"一执行就炸"的假 session 钉住。

> **为什么不干脆替模型写结论。** 试过这个方向，放弃了：反例任务考的就是
> "识别并声明做不到"，引擎代写等于把判分口径改了 —— 数字会变好看，
> 但它不再说明模型有能力。这个项目的底线是假阳性比假阴性更该防
> （第二节），所以到这里为止。

#### 8.5 ⭐ 顺手做出来的东西：两个探针，和轨迹里补上指纹

这一轮排查暴露了一个**观测盲区**：`trace.json` 里只有动作和结果，
**没有页面**。明明看见 Agent 在原地打转，却没有任何字段能回答"当时页面到底变没变"，
最后只能另写脚本把动作序列重放一遍才量出来。

补了两件事：

| 产物 | 作用 |
|---|---|
| `StepRecord.page_fp` / `.stall_count` | 每步的页面指纹与停滞计数落进 trace，**直接读就行**，不用再重放 |
| `scripts/probe_page_fp.py` | 不调模型：量"滚动到底改不改指纹"（8.3 那个结论就是它测出来的） |
| `scripts/probe_replay_stall.py` | 不调模型：重放一次真实运行的动作序列，逐步打印指纹与停滞（8.4 的证据） |
| `scripts/analyze_stall_rules.py` | 不调模型：拿已落盘的指纹序列**离线对比两种判据**（见 8.6） |
| `scripts/show_failed_runs.py` | 不调模型：把**失败**的运行按**终止路径**摊开（8.14 的因果判断全靠它） |
| `scripts/show_run_answers.py` | 不调模型：把**通过**的运行也摊开——答案原文 + 证据核对状态，专治判分假阳性（8.15） |
| `scripts/choose_oscillation_rule.py` | 不调模型：在已落盘指纹序列上离线比七组振荡候选判据、扫 n/w 参数（8.15.2） |

后两个是配套的：一个看"失败为什么失败"，一个看"通过是不是真的通过"。
只做前者会漏掉本项目最贵的那类错 —— **分数涨了，但涨的全是假阳性**（8.15.3）。

#### 8.6 用数据选判据，而不是靠口味

停滞判据有两种自然写法，都说得通，代价却不同：

| 判据 | 规则 |
|---|---|
| **A. 同页连续** | 相邻两帧指纹相同就 +1，变了清零 |
| **B. 未见新页** | 当前指纹"以前出现过"就 +1，没见过就清零 |

B 看着更强（能抓住"在两个已知页面之间来回跳"这类交替循环，A 抓不住）。但把它
拿已落盘的指纹序列算一遍（`scripts/analyze_stall_rules.py`，阈值 6）：

```
                            步  完成     A最大  A首次触发   B最大  B首次触发
20260921-230335-t04         20  未过       6       20      6       20
20260921-230842-t06         20  未过       2        -      6       20
20260921-231051-t04         20  未过      12       14     12       14
20260921-231205-t05         17  通过       5        -      6       17   ← B 会喊停
规则 A 触发 3/13；其中本来通过的有 1 次
规则 B 触发 6/13；其中本来通过的有 2 次
```

两条结论都很硬：

1. **B 救不了 t06**：它也要等到**第 20 步**才够阈值 —— 也就是步数上限已经用完了。
2. **B 的误伤候选更多**：会在一次**通过**的 t05 运行里就喊停。

所以选 A。这不是口味，是算出来的。

> ⚠️ 这个脚本的口径必须说清：它只回答"**这段已经落盘的指纹序列会不会触发**"
> —— 那是个纯函数，没有不确定性。它**不**回答"触发之后模型会怎样"。
> 上一轮就是拿"旧轨迹重算"去证明"改动没有副作用"，然后被一次真基线打脸。
> 所以它的结论只能用来**排除明显更差的规则**，不能用来宣称"改了会更好"。

#### 8.7 数字（诚实版）

三次真基线，同一套任务、同一个模型（Qwen2.5-7B-Instruct）、各 3 轮：

| 任务 | 提交版（累计判据） | 本版（连续 + 停滞）① | 本版② |
|---|---|---|---|
| t01 / t02 / t03 | 3/3 · 3/3 · 3/3 | 3/3 · 3/3 · 3/3 | 3/3 · 3/3 · 3/3 |
| t04 | **0/3** | 1/3 | 1/3 |
| t05 | 3/3 | 1/3 | 2/3 |
| t06 | 2/3 | 2/3 | 1/3 |
| **合计** | **14/18** | **13/18** | **13/18** |

**这会读起来像一次退步，所以必须把话说清楚：**

- **t04 是修好的那一条**：提交版 0/3 是"被累计判据误杀"，现在不再误杀。
  t04 剩下的低通过率**不是熔断造成的**，是引擎/模型的真实缺口：
  必应首页的搜索框输入之后，`click` 提交按钮**一直超时**，三次里只有一次
  按了 Enter —— URL 从头到尾停在 `cn.bing.com/`，**根本没搜出去**。
  现在熔断日志写的是"页面连续 6 步毫无变化"，这是**如实**的；
  以前写的是"动作 `scroll#up` 累计 5 次"，那是不实。
- **13 vs 14 的差不能归因于我。** t05 在这几轮里是 3/3 → 1/3 → 2/3，
  t06 是 2/3 → 2/3 → 1/3 —— 同一套代码内部的摆动就有 ±1 轮以上。
  t05 那两次失败是模型**自己**的两种毛病（在登录页拿假账号反复试、
  以及编出一句"用户名或密码错误"当结论），都不是熔断引起的。
  单看 18 次运行分不出 13 和 14。
- **t06 没修好。** 这是本轮最该坦白的一条。它的失败形态是
  "**在 4 个已知页面之间来回跳**"（首页 ↔ 商品页 ↔ 分类页），
  而每一次跳转在指纹层面**确实是一帧新观测** —— 任何"没有新信息"的判据
  都只能等到步数上限附近才敢确认（8.6 那张表里 A、B 两条都到第 20 步）。
  加上收束拦截之后，它至少**不再是无声地烧完 20 步**，而是带着明确的
  "收束后又连续 3 次拒绝给出结论"熔断 —— 诊断清楚了，但仍不是通过。
- 所以这一节的结论是：**判据的语义修对了，机制是真的在动（trace 里可见），
  但没有让总分变好。** "加了一个机制"≠"解决了那条任务" —— 这已经是本项目
  第三次撞上同一句话了。

#### 8.8 ⭐ 把 30 次运行按"终止路径"分堆 —— 因果判断靠这张表

13 vs 14 争不清楚，是因为只在看"通过/不通过"。把 `error` 字段分堆就清楚了
（本版代码的全部 30 次运行，t01–t06）：

| 任务 | 通过 | 熔断·步数上限 | 熔断·收束拒答 | 熔断·连续失败 | 合计 |
|---|---|---|---|---|---|
| t01 / t02 / t03 | 9 | 0 | 0 | 0 | 9 |
| t04 | 3 | 1 | **2** | 1 | 7 |
| t05 | 3 | **4** | 0 | 0 | 7 |
| t06 | 2 | **5** | 0 | 0 | 7 |

这张表同时推翻了两件事：

- **收束拦截只在 t04 触发过 2 次**，从未在 t05 / t06 上触发。
  所以 "13 vs 14 不能归因于这套机制" 现在有直接证据，不是辩解。
- **t05 / t06 的 9 次失败，9 次都是"步数上限耗尽"**（最大停滞只有 1–4，
  离阈值 6 差得远）。模型不是在原地打转，是在**慢慢地、成功地乱走** ——
  每一步都换了页面，只是始终没走到"给结论"。

再看通过的那几次用了多少步：

| 任务 | 通过的步数 | 失败的步数 |
|---|---|---|
| t05 | 15 / 17 / 19 | 20 ×4 |
| t06 | 10 / 18 | 20 ×5 |

**t05 是卡在预算边上的** —— 它其实会收敛，只是要 15~19 步，而预算是 20。
也就是说：**这几条任务的主要瓶颈是步数预算，不是熔断器。** 顺着这条查下去见 8.9。

#### 8.9 ⭐ 真瓶颈是步数预算：20 → 30

拿上面那个假设直接验：同一套代码、同一个模型，只把预算放到 30，重跑同样 12 次。

| 任务 | 预算 20 | **预算 30** |
|---|---|---|
| t04 | 2/4 | **4/4** |
| t05 | 1/4 | **2/4** |
| t06 | 1/4 | **4/4** |
| **合计** | **4/12 = 33%** | **10/12 = 83%** |

关键证据：**t06 通过的那三次用了 21 / 23 / 25 步 —— 全都超过旧的 20 上限。**
那三次在旧预算下**注定失败**，不是模型做不到，是预算用完了。

这把实验 7 的一个判断也顺带修正了：当时看到"7B 和强模型在 t06 上都是 2/3"，
推断"两边都栽 ⇒ 更像骨架问题"。方向对（确实是引擎侧），但**定位错了** ——
不是熔断器不够强，是预算太紧。

**这不叫"挪尺子"，但必须把界线讲清楚：**

| | 判分参数 | **产品参数** |
|---|---|---|
| 例子 | `must_contain`、拒答措辞、`kind` | `MAX_STEPS`、超时、并发 |
| 动了会怎样 | **口径变了**，前后数字不可比 | 口径不变，**成本变了** |

`MAX_STEPS` 属于后者 —— 它回答"这个 Agent 愿意为一个任务花多少步"。
改它不违规，但**代价和前后数字都要写出来**：

- 失败的任务会更贵（以前 20 步停，现在可能烧到 30）；
- 但三条难任务的**平均耗时反而从 100 秒降到 75 秒** ——
  因为失败的运行是"烧满预算"的，成功的运行"做完就停"，
  把一批注定烧满的失败变成中途成功，总账是省时间的；
- ⚠️ **本项目早先的 `15/18`、`14/18`、`13/18` 三组基线都是 `MAX_STEPS=20` 下跑的**，
  和 30 下的数字**不能直接比**。

所以评测脚本也一并改了：**步数预算现在会打进报告头部和每一条明细**
（`eval/run_eval.py` 的 `max_steps` 字段），和 `model` 字段同等对待。
规则是：**凡是会改变结论的参数，都必须跟着数字一起走。**

> ⚠️ **这一节的结论后来被自己的基线打回来一半。** 完整基线（六条任务、
> `--repeat 3`、预算 30）跑出来 t06 只有 **1/3**，不是 4/4 ——
> 那组 10/12 里的 t06 是**运气**，合并七次看真实水平是 5/7。
> 而且 t06 的失败形态是**交替跳页振荡**，加预算根本治不了。
> 见 8.12。

#### 8.10 ⭐ 一次"看起来参数是对的"：预算被 `.env` 静默按在 20

8.9 把默认值从 20 改成 30 之后，按计划重跑完整基线验证。跑了 8 分 45 秒，
翻开轨迹，最后一行是：

```
达到最大步数上限（20），任务未完成
```

**预算还是 20。** 而报告头部打印的也是"步数预算 20"，一切看起来都正常 ——
因为 `.env` 里那句遗留的 `MAX_STEPS=20` 覆盖了代码默认值。于是
"我改了代码"和"实际生效的值"之间隔着一个**看不见的覆盖**：
改与不改，从报告上完全看不出区别。

差一点就把这份 20 预算下的基线当成 30 的报出去，并把"数字没变"读成
"这次修复没用"。**最讽刺的是：8.9 的注释里已经写下了这条警告**
（"跨版本对比时必须对齐预算"）—— 警告写下来了，但没有任何东西替你检查。

修法不是"下次记得看"，而是让来源变成**可打印、可落盘的事实**：

| 改动 | 作用 |
|---|---|
| `config.resolve_int(name, default) -> (值, 来源)` | 来源只有三种：进程环境变量 > `.env` 文件 > 代码默认值 |
| `MAX_STEPS_DEFAULT` 抽成模块常量 | 原先这个数写在三个地方（`Settings` 的 `default_factory`、`.env`、`.env.example`），漂移的口子就是它给的 |
| 头部改打 `步数预算 30（来自 .env 文件）` | 值与代码默认值**不同**时额外黄字警告"跨版本对比必须对齐这一档" |
| 报告顶层加 `max_steps` / `max_steps_source` / `max_steps_default` | 拿两份 `eval_*.json` 对比时，第一眼就能看清是不是同一档 |

要分清"真环境变量"和"`.env` 文件"，必须在 `load_dotenv()` **之前**快照
`os.environ` —— 它默认不覆盖已存在的变量，加载之后两者就分不清了。
另外加了一条**防漂移测试**：仓库里提交的 `.env.example` 必须写着
`MAX_STEPS={MAX_STEPS_DEFAULT}`。`.env` 是本机副本、CI 上不存在，
`.env.example` 才是新人 clone 之后照着填的那份，两者不一致 =
新人拿到的预算和文档说的不是一回事。

> **教训：把参数值打印出来 ≠ 参数是对的。**
> 生效值和"它从哪儿来"是两件事。会改变结论的参数，
> 它的**来源**也是结论的一部分。
> （顺带核实掉一个疑点：早先几份 `eval_*.json` 里每条明细都没有 `max_steps`
> 字段 —— 查了 `git show db59baf` 才确认那字段是 e983e2f 才加进 `run_task`
> 返回体的，不是落盘被过滤。也就是说 8.9 里那两组数字（4/12 与 10/12）的
> 预算**只存在于当时的终端输出里**，文件里复核不了。如实记下，不假装可复核。）

#### 8.11 t04 动作层的真实形态：不是"提交按钮超时"，是模型在点不该点的东西

上一版 8.10 把 t04 的缺口写成"必应首页 `click` 提交按钮**稳定超时**，
三次里只有一次按了 Enter，该查超时值（**3000ms 可能偏短**）"。
把 30 条 t04 轨迹翻完之后，这句话**三处都不准**，先收回：

| 原说法 | 实测 |
|---|---|
| 提交按钮稳定超时 | 超时的目标不是提交按钮，是**必应首页「热点资讯」的新闻标题**（`<a title="钟南山团队发现肺结节新趋势">`）和**已隐藏的菜单项** |
| 超时值 3000ms，可能偏短 | 实际 `STEP_TIMEOUT_SECONDS=30`，即 **30 秒**（报错原文 `Timeout 30000ms exceeded`）。不是太短，是**太长** —— 每次失败白等 30 秒 |
| 该从推理/提示词入手 | 有一部分是，但**观测层的锅更直接**（见下） |

统计每条轨迹里"输入搜索词之后的第一个动作"（30 条轨迹，每条一个 ——
其中 29 条是 9/19~9/21 的历史运行，1 条是今天跑在错误预算上的那次）：

| 输入之后的动作 | 次数 | 结果 |
|---|---|---|
| `press Enter` | 7 | **7/7 全成功** |
| `click` 某个 ref | 12 | 8 成功 / **4 超时** |
| `extract`（先读页面再定） | 9 | 全部成功 |
| 动作输出不合法（`ref` 不是整数） | 2 | 白费一步 |

**按 Enter 的 7 次一次没失手。** 真正的缺口是：模型只有大约四分之一的时候
去按 Enter，其余时候点了一个 ref，而那个 ref 指向的东西根本点不动 ——

- `<a target="_blank" title="钟南山团队发现肺结节新趋势">`：必应首页资讯流里的
  新闻标题。这类元素**持续轮播**，而 Playwright 点之前要等元素"稳定"
  （相邻两帧包围盒不变），轮播元素**永远等不到**，于是耗满 30 秒；
- `<li id="academic" role="menuitem">`，以及另一条的
  `element is not visible`：感知时可见、点击时已隐藏的菜单项；
- 同一个 ref 连点三次（第 15/16/17 步都点 `ref=9`）：因为喂回去的报错是
  Playwright **原样透出的多行 call log**，模型读不出"这个目标永久点不动、
  换条路"，只能重试 —— 三步就是 90 秒。

代价是实打实的：单次失败的 t04 跑了 **397 秒**（20 步）。

所以这条缺口该定位在**观测层 + 动作层**，不是"必应不好对付"：
感知层收集元素时只判断"此刻可见、有尺寸"，判断不了"点得动"
（轮播中的元素此刻确实有尺寸，确实"可见"），而 `label()` 对空标签元素
只能给出空串 —— 元素清单里因此混着一批标签为 `「」` 的项，模型无从分辨。

#### 8.12 ⭐⭐ 预算 30 的完整基线：一次**没有复现**的改善

按 8.10 的建议补的完整基线留档（六条任务、`--repeat 3`、预算 30）：
`runs/eval_20260922-085119.json`

```
14/18（77.8%）｜ pass@3 100% ｜ pass^3 50%
normal 11/12 ｜ counter（反例拒答）3/6
平均步数 10.0 ｜ 平均成本 ¥0.02 ｜ 平均耗时 35.95 秒

t01 3/3   t02 2/3   t03 3/3   t04 3/3   t05 2/3   t06 1/3
```

按终止路径分堆，18 次运行里只有 4 次失败，而且**分属三个不同原因**：

| 任务 | 通过 | 终止路径 |
|---|---|---|
| t01 / t03 / t04 | 3 / 3 / 3 | 全部正常收尾 |
| t02 | 2 | 1 次 **模型连续输出非法格式**（21 步作废） |
| t05 | 2 | 1 次无 error、正常收尾但**结论错**（9 步） |
| t06 | **1** | 2 次 **步数上限耗尽（30）**，1 次 19 步通过 |

把两次预算 30 的样本合起来看：

| 任务 | 预算 20（n=4） | 预算 30（n=4） | 完整基线（n=3） | 预算 30 合并（n=7） |
|---|---|---|---|---|
| t04 | 2/4 | 4/4 | 3/3 | **7/7** |
| t05 | 1/4 | 2/4 | 2/3 | **4/7** |
| t06 | 1/4 | **4/4** | **1/3** | **5/7** |
| 合计 | 4/12 | 10/12 | 6/9 | **16/21** |

两半都要说，少一半都不诚实：

- **方向成立**：预算 20 → 30 确实让这三条从 4/12（33%）升到 16/21（76%）；
- **幅度被高估**：10/12 里的 **t06 4/4 是运气**，真实水平是 **5/7（71%）**。
  说"预算一调，难任务就 10/12"，等于把一次小样本的波动当成了机制效果。

> ⚠️ 前两列的预算**文件里复核不了**（详见 8.10 结尾）：那时 `max_steps` 还没进
> `run_task` 的返回体，只存在于终端输出里。

**更要紧的是：t06 的失败形态加预算治不了。** 两条 t06 失败都写「达到最大步数
上限（30）」，但形态是**在两个页面之间来回跳** —— 详情页 ↔ 目录页，反复点
"Add to basket"，从不收尾。**停滞计数全程只有 0~2（阈值 6）**：页面每步都在变
（A→B→A→B，每一帧都和上一帧不同），`page_fingerprint` 判不出"没有进展"。

这正是 8.1 里预判过、当时先记在账上的那个漏洞：

> 必然一边漏（交替滚动 / **交替跳页**绕过去）一边误杀（分散但正常的探索）。

所以 8.9 那条推断 **观察是对的、因果是错的**：它们确实都死于步数上限，
但**加预算并没有解决它** —— 真因是没有一条判据能让它停下来。这也解释了
8.9 里当时想不通的那件事（"为什么动态延长预算对 t05/t06 无效"）：
问题从来不在"给多少步"。

#### 8.13 顺带挖出的第二个真缺陷：`ref` 与 `dy` 字段被写混

三条失败运行**都在第 20 步**撞上同一个动作解析错误。原文：

```
模型输出不是合法 JSON：动作字段不合法:
  [{'type': 'int_parsing', 'loc': ('ref',), 'input': 'dy=500', ...}]   # 把 dy 写进了 ref
  [{'type': 'int_parsing', 'loc': ('ref',), 'input': 'None',   ...}]   # 想表达"没有 ref"
```

t02 那次更贵：第 6 / 19 / 20 / 21 步**连续犯**，触发「模型连续输出非法格式」
提前中止 —— **21 步全部作废**。

两个都算不上"模型太笨"，但**改法不同**：

- `"None"` / `"null"` / `""` 表示"该字段没有值" —— **无歧义**，应当接受；
- `"dy=500"` 是**字段写混**，但**不该猜**：猜成"滚动 500 像素"等于替模型做了
  语义决定，可能执行一个它没打算做的动作。正确做法是**把话说清楚**
  （报错直接点明"你把 `dy` 写进了 `ref`"），让它自己改。

⚠️ **不许当成"已验证有效"**：修完必须单独量边际效果。另外 `raw_action` 存的是
`"(格式错误)"` —— 模型原始输出没有留档，这次只能靠 pydantic 的 `input` 倒推，
是个观测缺口。

#### 8.14 下一步

按 8.12 的结果排序，现在有三个明确的工程缺口（不再是"唯一一个"）：

1. ⭐ **t06 的振荡判据（优先级最高）**：8.12 证明它的失败是**交替跳页**，
   停滞计数全程 0~2、现有两种熔断都抓不到，加预算无效。要补一条能识别振荡的判据
   （例如"同一对页面之间来回超过 N 次、且每次都确认过没有目标功能，就必须 finish"）。
   这一条同时解决两件事：让失败的任务**收敛**，以及让通过的任务**更省**
   （t06 通过时也要 19~25 步）。
2. **动作层：`_click` 超时后的报错要译成人话**：输入搜索词之后，模型只有约四分之一
   的时候按 Enter（**按了 7 次，7 次全成功**），其余时候去点一个实际上点不动的 ref，
   每次白等 30 秒。现在喂回去的是 Playwright **原样透出的多行 call log**，
   模型读不懂，于是同一个 ref 连点三次（见 8.11）。
   - 连带**观测层**：元素清单里空标签项（显示成 `「」`）太多，模型无从分辨。
     `label()` 目前只用 `innerText || value || placeholder || aria-label ||
     title || name`，可以补上关联 `<label for=…>` 或 `id` 这类线索。
   - ⚠️ **不要**去动超时值：30 秒不是"太短"，问题在等了一个注定等不到的条件。
     缩短它只是让同一个失败更快发生，不改结果。
3. **动作解析：`ref` 与 `dy` 写混要能纠回来**（见 8.13）：`"None"` 这类无歧义输入
   应当接受；`"dy=500"` 这类字段写混**不许猜**，但报错要点明"你把 `dy` 写进了 `ref`"。
   顺带补上 `raw_action` 的留档 —— 现在存的是 `"(格式错误)"`，模型原始输出丢了。
4. 把 `--repeat` 提到 5~6 再比较版本 —— 3 轮分不出 13 和 14，**8.12 就是被这件事
   教训的**（t06 在 4 次样本里 4/4，在 3 次样本里 1/3）。
5. 视觉通道的描述每帧措辞不同，会让指纹一直变、把停滞检测"喂"成永远有进展
   （已写在 `page_fingerprint` 的已知局限里）。等它真成为瓶颈再动。

> 消融规矩：2 和 3 都是**会改变模型所见**的改动，修完必须**单独量边际效果**，
> 不许与 1 混在一起报"变好了"。

| `LLM_MODEL` | `deepseek-chat` | 模型名 |
| `VLM_API_KEY` | 空 | 视觉通道的 key。**留空则自动跳过视觉降级**，只走 DOM |
| `MAX_STEPS` | 30 | 单个任务的最大步数。**这个值实测调过**：20 → 30 让三条难任务从 4/12 升到 16/21（合并两次样本；见第八节 8.9 与 8.12）——它不只是"防死循环"，也是"愿不愿意等模型想清楚"。⚠️ 但**别把 10/12 当成稳定值**：那一组里的 t06 4/4 是运气，真实水平 5/7，且 t06 的失败是振荡、加预算治不了 |
| `STEP_TIMEOUT_SECONDS` | 30 | 单个浏览器动作的超时 |
| `HEADLESS` | `true`（代码默认）/ `false`（`.env.example` 里显式写成 false） | true = 不显示浏览器窗口。脚本、服务、CI 都该无头；本地想看浏览器跑就填 false |
| `TEARDOWN_TIMEOUT_SECONDS` | 8 | 浏览器收尾的总时间预算。超了放弃等待（任务状态不受影响），见「控制台暴露出来的四个真实缺陷」第 4 条 |
| `BROWSER_PROXY` | 空 | 浏览器出口代理，如 `http://127.0.0.1:7890`。**留空 = 不传 proxy 参数**，跟随浏览器自身默认 |
| `BROWSER_PROXY_BYPASS` | 空 | 不走代理的域名，逗号分隔，如 `baidu.com,taobao.com` |

> 为什么代理要单独配一份，而不是跟随系统代理：系统代理是全局的，
> 但浏览器该不该走代理取决于目标站点，一刀切两边都会坏。
> 本机实测的真实约束 —— 国内站点经境外节点时淘宝只回 139 字空壳、
> 百度直接 `ERR_CONNECTION_CLOSED`；而 GitHub / Google 不走代理又连不上。
> 想让两边都能跑，就填 `BROWSER_PROXY` + 把国内域名列进 `BROWSER_PROXY_BYPASS`。

## 成本是怎么算出来的

`llm.py` 里每次调用都会把 `prompt_tokens` / `completion_tokens` 累加进
`Usage` 对象。每次运行结束，CLI 会打印：

```
token        输入 8432 / 输出 1105 / 共 9537
模型调用     9 次
估算成本     ¥0.010642
```

单价在 `config.py` 的 `price_in_per_mtok` / `price_out_per_mtok` 里，
按你实际用的模型改。**注意这是估算**——真实计费以厂商账单为准。

## 目前的能力边界（诚实版）

已知做不到、或者做得不好的地方：

- **引擎不会替你登录**（也不该保存你的密码）。遇到登录墙它会**把控制权交给你**：
  打开一个真实浏览器让你自己登，登完自动接着干（见下面两条）。
  引擎手上永远没有凭据 —— 这是设计，不是缺失。
- **不处理验证码**。滑块、点选一律绕不过。
- **只在主 frame 里找元素**。`<iframe>` 里的内容目前看不见。
- **不解析 Shadow DOM**。Web Components 站点会走视觉通道。
- **视觉通道按整页截图理解**，不做元素级定位，所以它只能"描述"，
  最终点哪个编号还是得回到 DOM 通道。
- **没有持久化会话**。每次运行都是全新的浏览器上下文（断点续跑还在做）。
- **"来回跳"型循环：能识别、能提醒，但不会替你停。** 停滞检测认的是"页面变没变"，
  而在几个已知页面之间来回跳时，每一次跳转在指纹层面**确实**是一帧新观测 ——
  所以它抓不到；t06 那种"详情页 ↔ 目录页"的振荡连动作指纹也兜不住
  （两次点击之间夹着别的动作）。
  现在补了第三套判据 `oscillation_pages`（最近 4 步只在 ≤2 个**已去过**的页面
  之间来回），命中后**只注入一条提醒**，不进收束、不拦动作。
  为什么不熔断：离线在已落盘轨迹上比过七组候选判据，最好的一组
  "受害运行 19/19 全抓到，但已收敛的运行里也有 29/62 会触发（含 11 条 normal）"——
  **该抓的不漏，不该抓的也误伤近一半**，拿去熔断会连 t04 的正常往返一起打掉。
  **实测效果（`--only t04 t05 t06 --repeat 4`，判分修正后同一把尺子）**：
  反例两题 `t05` 2/4 → 4/4、`t06` 2/4 → 4/4（步数从"耗尽 30 步"变成 12~19 步收尾），
  合计 8/12 → 10/12；但 `t04` 从 4/4 掉到 2/4 且**原因未查清**
  （读 trace 确认：失败那两次**根本没收到警告**，见 8.15）。
  过程里还拆穿了一次"12/12"的判分假阳性 —— 完整复盘见第八节 8.15。
  ⚠️ 这里曾经写着"这类循环未必真卡住 —— t06 在预算 30 步后是 4/4，它只是在慢慢地
  想，不是在原地死转"。**那句话已被自己的基线推翻**（4/4 是小样本波动，合并七次
  是 5/7），见第八节 8.12 / 8.14。
- **必应首页上会点不动一些元素**。输入搜索词之后，模型只有约四分之一的时候按
  Enter（按了 7 次全成功），其余时候去点必应首页「热点资讯」里的**新闻标题**
  （这类元素在轮播，Playwright 等不到它"稳定"，耗满 30 秒）或**已隐藏的菜单项**。
  根因在观测层与动作层，不在站点（见第八节 8.11）——
  原先这里写的是"`click` **提交按钮**稳定超时"，已更正。
  ✅ **2026-09-22 已修**（`browser.translate_click_error`）：超时不再回一句
  `Timeout 30000ms exceeded`，而是按原因翻译成"一直在动（轮播）/ 被浮层挡住 /
  当前不可见 / 在视口外"，并**明确禁止再点同一个**。修的是"模型拿到无用报错
  只能重试"这一段；"元素确实点不动"这件事本身没变。
- ✅ **`ref` 有时会被模型写成别的字段**（2026-09-22 已修，见 `models._coerce_int`）。
  实测出现过 `"ref": "dy=500"`（把 `dy` 写进 `ref`）与 `"ref": "None"`，都会让该步
  动作直接判非法；最贵一次连续犯 4 步，触发「模型连续输出非法格式」提前中止，
  **21 步全部作废**（见第八节 8.13）。
  修法划了一条线：**无歧义的直接掰正**（`"12"`→12、`"None"`/`""`→None），
  **有歧义的绝不猜**（`"dy=500"` 不替它翻译成滚动 —— 那是替模型补动作参数），
  但报错里直接写出正确写法。解析失败时模型原文存进 `StepRecord.raw_output`。

- **需要登录的站点**（✅ 2026-09-22 已处理，见第八节 8.18 / 8.20）
  ~~在登录页和内容页之间反复横跳，登录登不进去、内容也找不到。~~
  现在：感知层能识别登录墙 → 引擎**把控制权交给人**去登录（CLI 按回车 /
  控制台点按钮）→ 登录后自动回到任务入口、并清空旧的循环判据 → 再找内容。
  没人能登录时，明确告诉模型"顺序是先登录再找内容，别再切换"，而不是继续烧步数。
  注册表里标了 `needs_login` 的站点，这份知识现在会**一路传到引擎**
  （`/resolve` → 请求体 → `requires_login`），并自动改用有头模式起浏览器。
  **真机验证（2026-09-22）**：`https://github.com/login` 上 4.5 秒、
  **0 次模型调用**就识别出登录墙并进入 `waiting_login`，
  交出的是稳定可登录的页面（不是空白页）。
  ⚠️ 评测集里仍然没有会撞墙的任务，所以**没有基线数据**，只有真机冒烟 + 单测。
- ❌ **站点级的"反自动化"，目前无解**（2026-09-22 实测，BOSS直聘）
  它不是"需要登录"，而是**不许自动化**：搜索页会把页面跳成 `about:blank`；
  连**站点首页**也一样 —— 有头模式下载入首页，正常渲染出 **6399 个节点**，
  约 **2 秒后**由页内的 `browser-check-v2.js` 自己跳成 `about:blank`
  （整页只剩 3 个节点、39 字节，还会探测本机端口）。
  这意味着**人在那个窗口里也没法登录**（页面已经没了）。
  所以引擎现在的做法是：换到首页后等 3 秒复采，**确认那一页还在**才叫人；
  如果首页也是空白，就如实报「站点阻止了自动化访问」，
  **而不是弹一个"请去登录"让人白跑一趟**。
  这类站点（BOSS直聘、大概率还有领英/部分电商）在当前技术路线上拿不到数据，
  要么换站点，要么上真实用户配置的浏览器（未做）。

这些不是借口，是**待办清单**——也是你面试时可以主动讲的部分：
"我知道它在哪些情况下会失效，因为我都测过。"

## 双引擎：手写 ReAct 与 LangGraph（新增）

主循环有两个可互换的实现，用 `--engine` 切换：

```powershell
# 手写循环（默认，零额外依赖）
.\.venv\Scripts\python.exe main.py --task "读出页面标题" --url "https://example.com" --engine handwritten

# LangGraph 状态图（需 pip install langgraph langchain-core）
.\.venv\Scripts\python.exe main.py --task "读出页面标题" --url "https://example.com" --engine langgraph
```

### 为什么要两个都留着

**手写版**证明我理解循环本身：何时重试、何时熔断、怎么打断死循环。
**LangGraph 版**证明我会用主流框架，并且知道它在什么场景下值得引入。

两版共用同一套节点逻辑与终止条件，**A/B 实测完全等价**（mock 模式、同一任务）：

| | handwritten | langgraph |
|---|---|---|
| 步数 | 4 | 4 |
| 输入 token | 5300 | 5300 |
| 输出 token | 275 | 275 |
| 模型调用 | 5 | 5 |
| 成本 | ¥0.005850 | ¥0.005850 |

### 设计要点：终止条件抽成纯函数

`graph_agent.py` 里路由是纯函数，不依赖框架运行时，所以**状态机是可单测对象**：

```python
def route_after_act(state) -> Literal["perceive", "end"]:
    if state.get("finished") or state.get("error"):
        return "end"
    if state.get("step", 0) >= state.get("max_steps", 0):
        return "end"
    if state.get("consecutive_failures", 0) >= MAX_CONSECUTIVE_FAILURES:
        return "end"
    return "perceive"
```

> 踩过的坑：**LangGraph 只会传递 `TypedDict` 里声明过的 key**。
> 一开始我用 `_state` 这种下划线开头的键存页面状态，结果节点之间静默丢失，
> 报 `AttributeError: 'NoneType' object has no attribute 'render_for_prompt'`。
> 必须在 `AgentState` 里显式声明。

## 容器化（新增）

```bash
docker build -t browser-agent .
docker run --shm-size=1g -p 8000:8000 browser-agent -m uvicorn bagent.api:app --host 0.0.0.0
```

**必须给 `--shm-size`**：Chromium 在容器里常因 `/dev/shm` 太小而随机崩溃
（典型报错 `Target closed` / `Page crashed`），默认 64MB 不够。

基础镜像用 Playwright 官方的 `mcr.microsoft.com/playwright/python`，它已装好 Chromium
和全部系统依赖；自己从头 `apt install` 既慢又容易漏库（缺 `libnss3` / `libatk` 时报错很
不直观）。容器内默认 `HEADLESS=true MOCK=true OFFLINE=true`。

非 root 运行：浏览器里跑的是「模型生成的页面操作」，权限必须收窄。

镜像默认命令是 `python main.py --help`；`ENTRYPOINT` 只固定解释器，
所以 `docker run 镜像 -m uvicorn ...` 会被正确拼成 `python -m uvicorn ...`。

> 本仓库**没有**附带 `docker-compose.yml`。上面那条 `docker run` 就是完整的启动方式；
> 想和 pr-review-agent 一起编排的话，那个文件需要你自己按需写。

### 构建踩过的两个坑

1. **`.dockerignore` 排除了 `docs/`，而 Dockerfile 里又 `COPY docs/ ./docs/`** —— 构建会直接
   报 `not found`。`docs/` 放的是实验记录和教程，属于要进镜像的内容，不能忽略。
   排查方式：把 Dockerfile 里每条 `COPY` 的源路径与 `.dockerignore` 的规则对一遍，
   凡是「既存在又被忽略」的就是雷。
2. **`doctor()` 把「视觉通道未配置」判为失败。** 视觉是 DOM 通道失效时的**可选**降级路径，
   没配 key 就自动退回纯 DOM，这是设计行为而不是故障。原来它返回 `settings.vlm_enabled`，
   导致容器里（`MOCK/OFFLINE`）自检退出码恒为 1。现已改为：配了才算一项检查，
   没配则如实说明「按设计只走 DOM 通道」；同时在 `MOCK/OFFLINE` 下跳过模型连通性检查，
   不在离线环境里发起真实网络请求。

## Web 控制台

服务启动后直接打开 <http://127.0.0.1:8000/> 就是一个自带的可视控制台
（深色主题，零前端依赖、无构建步骤）：

- 提交任务、选引擎 / 最大步数 / 离线开关，页面上直接看执行时间线；
- 每一步显示动作名、说明与所在网址，失败步用红色标出来；
- 下方「最近任务」表格列出最近 20 条，含步数与耗时（**点一行就能回看那条任务**）。

### 遇到登录墙时控制台会做什么（2026-09-22）

控制台里有个 **「显示浏览器窗口」** 开关，**默认勾上**。它不是一个"看着放心"的
装饰 —— 它是"人工登录"这条路的前提：无头模式下没有窗口，交接只能被诚实地拒绝。

流程：任务被识别成登录墙 → 状态变成 `等待登录` → 结果区弹出登录框，
告诉你**为什么判定是墙**、以及**要登录哪个页面** → 你在弹出的浏览器窗口里登录 →
点「我已完成登录，继续」→ 引擎回到任务入口重新开始（并清空旧的循环判据）→ 继续找内容。
登不进去就点「放弃登录」，任务按"未登录"如实收尾，不会假装成功。

三个刻意的取舍：

- **默认有头**：本地开发用控制台，看得见浏览器才有意义；
  容器/服务器里用 `.env` 的 `HEADLESS=true` 保持无头。
- **交接整个运行只发生一次**（`handoff_tried`）。人已经表态过（登录了或放弃了），
  再问就是打扰，而且会把运行时间耗在等事件上。
- **换到首页后会等 3 秒再复采一次**，确认那页**还在**才叫人。
  这是被实测逼出来的：BOSS直聘 首页渲染完 2 秒就自毁，立刻采样会采到它
  还活着的那一瞬间，于是把人叫来、人一到页面就没了 —— 比不叫更糟。

实现方式刻意做到最简：`src/bagent/web/index.html` 是**单文件**页面，
用 `FileResponse` 直接从包内路径吐出去 ——

```python
_WEB_INDEX = Path(__file__).resolve().parent / "web" / "index.html"

@app.get("/", include_in_schema=False)
def console() -> FileResponse:
    ...
    return FileResponse(_WEB_INDEX, media_type="text/html; charset=utf-8")
```

几个取舍值得说明：

- **用 `Path(__file__)` 而不是相对 cwd 的路径**：静态页放在包内部，
  `pip install` 后依然找得到，也不受启动目录影响。
- **`include_in_schema=False`**：`/` 是给人看的页面，不是 API，
  放进 OpenAPI 只会让文档里多一条没有意义的接口。
- **页面自证可用**：`tests/test_api.py` 里断言 `/` 返回 `text/html` 且包含
  `id="task"` / `id="go"` 等锚点。一旦 Dockerfile 或打包清单漏掉 `web/` 目录，
  测试会立刻红，而不是等线上打开发现 404。

### 控制台暴露出来的四个真实缺陷

把后端接到一个真实界面上之后，原先"接口能返回 200 就算对"的地方全部露了馅。
这四处都是**后端逻辑问题**（不是渲染问题），控制台只是让它们变得可见：

1. **离线任务的成本是凭空算出来的。** 离线替身的 token 是按字符估算的，
   而 `cost_yuan` 照常乘以单价，于是离线跑一次会显示 `¥0.00347` ——
   使用者会以为这次真的花了钱。更根本的问题是同一件事有两个开关：
   选 LLM 客户端读 `req.mock`，判定是否计费读 `settings.mock`，而
   **`Settings` 上当时根本没有 `mock` 这个字段**，`st.mock = True` 是一句无声的空操作。
   现已在 `Settings` 上真正定义 `mock`，并由 `_run_task` 按请求覆写，
   `RunResult.offline` 把口径一路带到界面（显示 `¥0 / 成本（离线，未产生费用）`）。
2. **`records` 里的步号会跳号**（实测 `[1, 3, 4, 5]`）。模型输出不是合法 JSON 时，
   那一轮**确实消耗了一次模型调用**，但代码直接 `continue`，没有留下 `StepRecord`。
   审计轨迹看起来像"漏了第 2 步"，其实那一步的失败被整个吞掉了 ——
   排障时最不该丢的恰恰是失败那一步。
   修的时候踩到一个坑：不能给 `action` 塞一个编造的 `"(格式错误)"`，
   因为 `ActionName` 是封闭字面量，pydantic 会在构造时直接 `ValidationError`
   （等于"为了记录一个格式错误，先让程序崩掉"）。
   正确做法是 `StepRecord.action` 放宽为 `Action | None`，另加 `raw_action` 承载原始字符串。
3. **列表接口不返回 `steps` / `elapsed_seconds`**，导致前端表格这两列只能显示 `-`，
   除非客户端对每一行再打一次详情接口（20 行 = 21 个请求）。这两项在列表数据里本来就是现成的。
4. **任务"跑完了"却永远显示在执行中。** 这条最要命，因为它把成功伪装成卡死。
   终态原本写在 `async with open_browser(...)` **之后**，而浏览器收尾
   （`context.close()` / `browser.close()` / `playwright.stop()`）在某些环境下
   会长时间不返回 —— 收尾卡住 = 终态永远不写 = 控制台一直转圈。
   实测：一个离线任务 **3.3 秒**就走完 5 步（每步的时间线都是实时可见的），
   但 **150 秒**都没进终态；CLI 更直白，报告早就打完了，进程却卡在收尾上
   4 分钟不退出。这里的关键认识是：**收尾不属于任务本身**，它只负责回收进程资源，
   不该决定"任务完成了没有"。修法是两层：

   - `BrowserSession.__aexit__` 给整个收尾一个总时间预算
     （`TEARDOWN_TIMEOUT_SECONDS`，默认 8 秒），超时记一条警告就放弃等待；
   - `_run_task` 不再用 `async with`，改成手动进入 + 在 `finally` 里收尾，
     这样终态能在收尾**之前**落表。

   注意这两层不是重复：第一层让 CLI 能自己退出，第二层保证即使别人换了个
   没有超时护栏的实现，服务端的终态也不会被拖住。回归测试
   `test_task_reaches_terminal_state_even_if_teardown_hangs` 用一个
   "收尾永不返回"的替身把这一点钉住了。

   顺带一个诚实的边界：超时放弃之后，那个 Playwright 驱动子进程会成为孤儿，
   Windows 上的 `asyncio` 在解释器退出时还会等它约 30 秒，并打印几条
   `unclosed transport` 的 `ResourceWarning`。也就是说 CLI 的**总**耗时可能到 40 秒
   量级 —— 但报告在 12 秒内就打完、任务状态也早已落表，剩下的只是进程回收。
   在 CI（Linux）上收尾约 1 秒完成，完全不会走到这条路。

前三条都补了回归测试，断言的是**语义**而不是返回值：
`test_offline_task_reports_zero_cost` 要求离线任务 `cost_yuan == 0`，
`test_step_record_accepts_error_step` 要求"格式错误"这一步能落盘且能序列化，
`test_task_reaches_terminal_state_even_if_teardown_hangs` 要求"收尾卡住也要进终态"。
