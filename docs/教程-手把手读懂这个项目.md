## 第 0 课：先跑起来，再理解

**先建立反馈**。看不懂代码的时候，最没效率的事就是硬啃。

```powershell
cd C:\Users\pc\Desktop\browser-agent

# 自检：确认每一环都通
.\.venv\Scripts\python.exe main.py --doctor
```

你会看到一张表，四个检查项。**只要有一项是"失败"，先别往下走**，
把失败那行的说明贴给我。

自检全绿后，跑第一个任务：


`--headful` 会弹出浏览器窗口。**盯着屏幕看**，你会看到：

## 第 1 课：ReAct 到底是什么

抛开所有代码，ReAct 的核心只有这几行：

```python
while not done and step < max_steps:
    state  = look_at_page()          # 看
    action = ask_llm(task, state)    # 想
    result = do(action)              # 做
    history.append(result)           # 记
```

**和"写死脚本"的本质区别在第 2 行。**

写死的脚本是：
```python
click("#next-page")     # 如果页面改版了？崩
read(".quote")          # 如果元素没加载出来？崩
```

ReAct 是：
```python
state = look_at_page()   # 实际看到了什么，就基于什么决策
```

所以 ReAct 天然抗变化——按钮文案改了、多了个弹窗、登录态过期，
它都会看到并自己绕路。代价是**慢**（每一步都要调一次模型）和**贵**。

**你现在应该能回答**：ReAct 用"慢和贵"换来了什么？

> 答：对页面变化的鲁棒性。写死的选择器一改版就崩，ReAct 会重新决策。

对应文件：`src/bagent/agent.py` 的 `run()` 方法。

## 第 2 课：LLM 层为什么这么"啰嗦"

打开 `src/bagent/llm.py`，你会觉得比"调 API"复杂得多。三个原因：

**① 超时 + 指数退避重试**

```python
delay = min(2 ** (attempt - 1), 8) + random.uniform(0, 0.5)
```

第一次失败等 1 秒，第二次等 2 秒，第三次等 4 秒，封顶 8 秒。
最后的 `random.uniform(0, 0.5)` 是**抖动**——防止多个实例同时重试，
把对端一次性打垮（这叫惊群）。

**② 认证错误不重试**

看这段：

```python
except openai.AuthenticationError as exc:
    raise LLMError("API Key 被拒绝...")
```

key 错了重试一百次还是错。**分清"值得重试的错"和"重试也没用的错"**，
是工程和玩具的分界线。

**③ 每次都记 token**

```python
self.usage.add(Usage(prompt_tokens=..., completion_tokens=...))
```

积累下来就是成本面板。没有这个，你根本不知道跑了 50 个任务花了多少钱。

**你现在应该能回答**：为什么要给重试加随机抖动？

> 答：避免多个客户端在同一时刻集体重试，形成新的流量尖峰。

## 第 3 课：感知层——`[3]` 这个编号是怎么来的

这是整个项目最巧妙的地方。看 `perception.py` 里的那段 JS：

```javascript
el.setAttribute('data-ba-ref', String(ref));   // 给元素打标记
out.push({ ref: ref, tag: ..., text: label(el) });
```

它做了三件事：
1. 找出所有可交互元素（`a` / `button` / `input` / `[role=button]` …）
2. 过滤掉看不见的（尺寸为 0、`display:none`、`opacity:0`、离视口太远）
3. **给每个元素写上 `data-ba-ref="编号"`，并返回一份清单**

于是模型看到的是这样一段文本：

```
可交互元素（点击/输入时请使用方括号里的编号）:
  [1] <a> Home
  [2] <a> Next →
  [3] <input> 搜索
```

模型回答 `{"action": "click", "ref": 2}`，动作层就能用
`[data-ba-ref="2"]` 精确定位。

**关键点：编号是在浏览器里现场生成的，不写死。**
页面变了，编号自然重新分配，模型每次看到的都是最新的。

**你现在应该能回答**：为什么不直接让模型输出 CSS 选择器（比如 `.next > a`）？

> 答：模型很难凭空猜对真实站点的选择器，而且选择器一改版就失效。
> 让它从"看得见的清单"里挑编号，准确率高得多。

## 第 4 课：动作层——为什么不按坐标点击

```python
locator = self.page.locator(f'[data-ba-ref="{ref}"]')
await locator.first.click()
```

如果按坐标点（模拟鼠标移动到 x=520, y=340 再点），会发生什么：

- 页面滚动了一下 → 坐标偏了 → 点空
- 突然弹出广告 → 坐标被遮住 → 点到广告上
- 字体渲染不同 → 元素位置差几像素 → 点空

编号不会。因为 `[data-ba-ref="2"]` 是一个**语义引用**，
不管元素在哪儿，浏览器都能找得到它。

另外注意 `_is_sensitive()`：

```python
SENSITIVE_PATTERNS = ("支付", "确认下单", "删除", "checkout", ...)
```

命中就要求人工确认。**这是 Agent 项目里最容易被忽略、但最重要的一行**——
没有它，模型一次误判就可能真的帮你把钱花出去。

**你现在应该能回答**：为什么非交互环境（比如 CI）里默认是"拒绝"而不是"同意"？

> 答：默认同意的护栏等于没有护栏。安全设计的默认值必须是保守的。

## 第 5 课：主循环——什么时候该停下来

`agent.py` 里有三种终止条件，缺一不可：

| 条件 | 代码位置 | 防的是什么 |
|---|---|---|
| 模型主动 `finish` | `if action.action == "finish"` | 正常结束 |
| 达到最大步数 | `for step in range(1, max_steps + 1)` + `else` | 死循环烧钱 |
| 连续 3 次失败熔断 | `if consecutive_failures >= 3` | 明知做不到还硬撑 |

第三种最容易被漏掉。没有它，模型可能在一个找不到的按钮上
反复重试 20 次才停——你已经为此付了 20 次调用的钱。

还有一个细节：

```python
history.append(desc)        # 失败原因写回历史
history = history[-12:]     # 只留最近 12 步
```

**失败必须变成信息。** 如果只是 `continue`，模型下一轮看到的页面和上一轮一样，
它很可能原样再试一次。写回历史并附上"不要重复这个动作"才是有效反馈。

`history[-12:]` 则是控制成本——历史越长，每轮 prompt 越大，钱烧得越快。

**你现在应该能回答**：如果把 `history[-12:]` 改成保留全部历史，会发生什么？

> 答：prompt 越来越长，成本随步数近似平方增长；而且早期无关的历史
> 会干扰模型判断。这是一个"成本 vs 上下文完整性"的权衡点。

## 第 6 课：改一个字，看一个变化（最重要的学习方法）

**光读代码学不会。必须做实验。** 下面五个实验按难度排列：

### 实验 1：把最大步数调到 2，看它怎么失败

```powershell
.\.venv\Scripts\python.exe main.py --task "打开名言网站首页，读出第一句名言" --url "https://quotes.toscrape.com/" --max-steps 2 --headful
```

观察：失败信息是什么？trace.json 里 `error` 字段写了什么？

### 实验 2：关掉 `--headful`，确认无头模式也能跑

```powershell
.\.venv\Scripts\python.exe main.py --task "..." --url "..." --max-steps 10
```

思考：无头模式跑得一样好吗？有没有哪一步在无头下更容易失败？

### 实验 3：改系统提示词，观察行为变化

打开 `agent.py`，在 `SYSTEM_PROMPT` 末尾加一句：

```
8. 每一步都必须先用 scroll 确认页面没有更多内容，再决定下一步。
```

重跑同一个任务，看步数和 token 怎么变。
**这是你第一次亲手做"提示词迭代"——把它记下来，就是简历里那条
「迭代 3 版规划提示词后成功率从 X 提升到 Y」的原始素材。**

### 实验 4：给感知层加一个过滤规则

在 `perception.py` 的 JS 里，把收集上限从 100 改成 30：

```python
MAX_ELEMENTS = 30
```

重跑，观察：
- token 消耗降了多少？
- 成功率有没有变化？在哪些页面上变差了？

### 实验 5：写一个你自己的任务

在 `tasks/examples.json` 里加一个你每天真会上网的场景。比如：

```json
{
  "id": "t07",
  "kind": "normal",
  "task": "在你所在城市的招聘网站上搜索『Java 后端实习』，读出前三个岗位的名称和公司。",
  "url": "https://www.zhipin.com",
  "expected": "三个岗位名 + 公司"
}
```

**这一条最有价值**——它是你自己想出来的需求，不是抄来的。

## 调试技巧

**看 trace.json**（每次运行都会生成）：

```
runs/20260919-103045-task/trace.json
```

里面有每一步的动作、成功与否、携带的 message，以及 token 和成本。
**Agent 出问题时，第一件事是打开 trace 看它在第几步走偏的。**

**看截图**：

```
runs/20260919-103045-task/shots/step_03.png
```

视觉通道激活时会自动存图。看一眼就知道当时页面上是什么。

**降日志级别看细节**：

```powershell
$env:LOG_LEVEL="DEBUG"
.\.venv\Scripts\python.exe main.py --task "..." --url "..."
```

## 下一步：把"感觉变好了"变成"数据变好了"

现在你只有 6 个示例任务，靠肉眼看结果。这还不够——面试官会问
"你说提升了，怎么证明？"

需要补的东西：

1. **固定评测集**：把任务扩到 12~20 个，每个标注预期结果
2. **自动判分**：跑完后自动比对，输出成功率 / 平均步数 / 平均 token
3. **版本化**：每次改提示词都存一份配置和结果，才能对比
4. **反例任务**：故意给做不到的任务，验证 Agent 会不会硬撑（现在有 2 个）

**这四个做完，你简历上那些数字才是真的。** 到那时我们再来改简历——
你会发现能写的东西比现在多得多，而且每一条你都能答到第八层。
