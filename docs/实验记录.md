## 实验 1：原始提示词 —— 失败

**时间**：2026-09-19 10:08
**任务**：打开名言网站首页，读出第一句名言的正文和它的作者是谁
**结果**：❌ 失败

| 指标 | 值 |
|---|---|
| 是否完成 | 否（达到最大步数上限 20） |
| 步数 | 20 |
| token | 输入 33160 / 输出 809 / 共 33969 |
| 成本 | ¥0.034778 |
| 耗时 | 47.87 秒 |

**失败现象**：模型在第 6 步的想法里已经写出「根据页面摘要，第一句名言是 Albert Einstein 的名言」——
**它读到了答案，却继续点击元素**，共点击 `[1]`（站点 logo）9 次，直到步数耗尽。

**根因**（两个，都不是"模型太笨"这么简单）：

1. **提示词没有说清"什么时候该收工"**。原来的规则只说"完成后必须 finish"，
   但没告诉模型"读正文就能得到答案时，不需要任何点击"。
2. **循环没有被检测**。原来只有"连续失败熔断"，
   而这个循环里每一步都是"成功"的——只是毫无进展。
   只判断成败，抓不到原地打转。

## 实验 2：强化 finish 规则 + 循环检测 —— 通过

**改动**（两处，都在 `src/bagent/agent.py`）：

**① 系统提示词新增「关于 finish」小节**，明确告诉模型：
- 大多数任务不需要点击任何元素，答案通常在「页面正文摘要」里
- 能从正文回答出来，**下一步必须是 finish**
- 不要点站点 logo（通常是最靠前的编号）、不要点翻页链接
- 某个动作连续两次没带来新信息就停

**② 新增动作指纹循环检测**：

```python
def _action_signature(action: Action) -> str:
    if action.action in ("click", "type", "goto"):
        return f"{action.action}#{action.ref or action.url}"
    ...
```

只取**动作名 + 编号**，刻意不看 `thought`——因为模型每次编的理由都不一样，
但实际执行的动作是同一个。**识别循环必须看行为，不能看说辞。**

阈值：同一指纹重复 3 次 → 往历史里注入强制警告（措辞用"禁止"而不是"建议"，
小模型只对强约束有反应）；重复 5 次 → 直接熔断，不再烧钱。

**结果**：✅ 通过

## 三个失败模式（这才是真正值钱的部分）

### ① t05：幻觉 —— 最严重的一类

任务：*登录名言网站，查看我账号里的收藏列表*（该站点**根本没有登录功能**）

模型输出了：

> 账号收藏的标签包括：change、deep-thoughts、thinking...

**它把页面底部的「Tags」区块当成了"用户收藏"**，然后煞有介事地编了一个答案出来。

这类错误比"答不出"危险得多，因为：
- 它看起来很可信，用户不核验就会被误导
- 现有的拒答护栏（`REFUSAL_MARKERS`）只在**回答里出现"无法/不能"**时才判定为正确放弃，
  而幻觉回答里一个这类词都没有

**改进方向**：需要让模型在给出结论前**自证来源**——
"这个结论来自页面的哪一段文字？"答不出来就不许输出结论。
这和项目二（PR 审查 Agent）里"无行号证据不评论"是同一个思路。

### ② t02：翻页后读错

要求读第 2 页第一句的作者（Marilyn Monroe），模型答成了 George。
10 步里应该是翻页后没重新定位到"第一句"，读串了。

**改进方向**：感知层给正文摘要时**按 DOM 顺序保留结构**，
现在是直接取 `innerText` 截断，首尾各 750 字，中间的翻页后内容可能被切掉。

> ✅ **这一条后来被证实了，而且比这里写的更具体**（见实验 4.2）：
> 不是"读串了"，是"**首句正文在头、它自己的作者被省略、尾部有个别人的作者**"——
> 模型被一份残缺的观察逼出了错误配对。首尾各 750 字这个截断方式就是病根。

### ③ t03 / t04：效率问题

t03 只用了 3 步就失败——说明它**过早下结论**，没真正遍历书籍列表找最高价。
t04 用了 17 步才成功（84.84 秒），说明在必应这种复杂页面上找不到北。

> ❌ **这一条是错的**（2026-09-21 复核，见实验 4.1）：
> t03 那 3 步**答对了**（£57.25 就是首页最贵），失败是判分真值写错造成的假阴性。
> 把"判分错"读成"模型过早下结论"，正是这份记录里最该引以为戒的一次误判。
> t04 的结论暂时没问题，它的真实症状是**原地打转熔断**。

**改进方向**：给感知层加一条"页面正文里的结构化数据要优先展示"，
比如表格、列表项按行输出，而不是把 innerText 打成一片。

# 实验 4：t02 / t03「两项全败」的追根 —— 两个反方向的教训

**时间**：2026-09-21 14:30 ~ 15:00

## 4.0 先说结论（因为它跟"我以为的"完全不一样）

`t02`（读第 2 页首句作者）和 `t03`（读首页最贵的书）连续三轮全败，
一开始被当成**同一个能力缺口**：模型动作之后凭假设收尾。
这个判断**错了**。动手改之前先去核了一遍，结果是两个完全不同的问题，
**而且一个都不在"模型太笨"这一侧**：

| 任务 | 真相 | 该改的是 |
|---|---|---|
| t03 | **判分真值写错了**（假阴性）。Agent 一直答对 | 任务文件 |
| t02 | **喂给模型的观察是残缺的**。正文摘要截断把"首句正文↔它的作者"切散了 | 感知层渲染 |

## 4.1 t03：真值写错了 —— 假阴性

任务文件里写的 `must_contain` 是 `["A Light in the Attic", "59.99"]`。

**换一条通道核**（不走浏览器、不经过模型，直接 HTTP 抓
`books.toscrape.com` 首页的 `price_color` 再排序）：

```
20 本书，最高价 £57.25 = "Our Band Could Be Your Life..."
A Light in the Attic 只有 £51.77
首页压根不存在 £59.99
```

而 Agent 三轮答的都是 **£57.25** —— 它一直是对的，是判分把它判错了。

**教训**：真值也是人写的、也会凭印象写错。而"凭印象写 expected"恰恰就是
本项目最想治的那个病（P0 那条"结论要有证据"）。
**真值有疑就必须换通道核，别拿浏览器里那一帧当唯一信源。**

> 已按核对结果改正 `tasks/examples.json`，并把核对过程写进该条的
> `_truth_source` 字段 —— 免得以后有人看到"t03 曾经全败"又去改 Agent。

## 4.2 t02：观察在骗模型（感知层问题，不是推理层）

逐帧还原：第 2 页正文 3449 字，而 `render_for_prompt` 这样截断：

```python
body[:750] + "\n...（中间省略）...\n" + body[-750:]
```

在这页上的实际分布是：

| 事实 | 原文字符偏移 | 落在 |
|---|---|---|
| 首句正文 "This life is what you make it…" | 26 | 头部 ✅ |
| **首句自己的作者 "by Marilyn Monroe"** | 1110 | **被省略** ❌ |
| 别人的作者 "by Elie Wiesel" | 2708 | 尾部 ✅ |

模型收到的观察是「**首句的正文在、它的作者不在，尾部孤零零躺着一个别人的作者名**」，
于是它把两者配成一对，答成 Elie Wiesel —— 三轮稳定复现。

**这不是幻觉，是观察本身在骗它。** 拿"看见 A 和 D、看不见 B 和 C"去问
"A 后面是什么"，答错是必然的。

### 修法（两处，都在 `src/bagent/models.py`）

1. **截断保序**：按**整行**只保留连续头部，如实说明"还有 N 行未显示、
   上面的内容与省略部分**不相邻**"。丢掉尾部是诚实的（模型知道该 scroll），
   拼接头尾是欺骗性的（模型会以为它们相邻，进而把它们配成一对）。
2. **正文预算 1500 → 3000**：实测三页长度 1668 / 3449 / 2029，
   1500 会把其中两页切成残缺状态。

## 4.3 顺带补的护栏：finish 必须带页面证据（`src/bagent/grounding.py`）

要求 finish 附一段**逐字从当前页面复制**的 `evidence`，且 answer 里那些
**在页面上确实找得到**的关键信息必须都出现在 evidence 里；对不上就**退回重做**
（上限 2 次，用尽后采纳答案但把 `grounded` 标 False —— 卡死会把"答错"
变成"没答案"，那是把问题藏起来）。

**边界要说清楚**：它管"结论有没有页面依据"，**不管"答得对不对"**。
一个证据抄得很忠实、但选错了书的结论照样能过（有用例专门钉住）。
判对错是 `judge` 的事。

### ⚠️ 诚实记录：这层护栏**没有**修好 t02

在只加了护栏、还没改截断的那一版上实测（`--only t02 --repeat 3`）：

```
t02 0/3 通过    证据 3/3「已核对」    平均 5.7 步
```

`grounded=True` 但答案仍是 Elie Wiesel —— 因为它引的
"by Elie Wiesel (about)" **确实逐字出现在第 2 页上**（那是第 7 句的作者）。
证据是真的，配对是错的：护栏拦不住"从同一页里挑错了那一行"。

**修好 t02 的是截断保序，不是这层护栏。** 护栏保留（它挡的是"凭记忆写证据"
和"引 A 答 B"），但不许把它写成 t02 的解药。

# 实验 5："代理开了但没用" + 一个真缺陷、一个被推翻的判断

## 5.0 起因

用户把本机代理开了（`127.0.0.1:7890` 确实在监听），想让真实站点评测
（`tasks/real_sites.json`，12 个站）多跑几个。第一反应：这下 7 个
`skipped` 能救回来了吧。

**结论是"没救回来"。但中间挖出一个真缺陷，还推翻了我在本实验草稿里
先写下的一个判断。**

## 5.1 真缺陷：预检和正式跑走的不是同一个出口

`eval/run_eval.py` 的环境预检自己裸开浏览器：

```python
browser = await pw.chromium.launch(headless=True)   # ← 无代理参数
```

正式跑的 `BrowserSession` 是读 `BROWSER_PROXY` 的。两边口径不一致，
后果不是"慢一点"，而是**结论会反**：配了代理、站点其实连得上，
预检却按直连去试、报"不可达"，任务在开跑前就被 `skipped` 剔除，
**一次都没跑**，报告里还看不出是被谁拦下的。

修法：判定只留一处 —— `src/bagent/browser.py::proxy_launch_kwargs()`，
两处共用。单测 `test_session_and_preflight_share_the_judgement`
用**源码级断言**钉住（谁再自己拼一遍 `{"server": ...}` 就直接红）。

## 5.2 代理实测：一个站都没多救回来

| 配置 | 12 个真实站点可达数 |
|---|---|
| 直连（不配 `BROWSER_PROXY`） | **5 / 12** |
| 走代理 `http://127.0.0.1:7890` | **5 / 12** |

可达：百度、GitHub、掘金、小红书、京东。
不可达：豆瓣、微博、当当、B 站、东方财富、12306 —— 两轮完全相同。

代理零改善 → 被拦的**不是"外网可达性"**。那是什么？

## 5.3 ⚠️ 先写错、后推翻：「浏览器 vs 非浏览器」这个框架是错的

我在草稿里先写下的结论是：

> 有些站 chromium 连不上、curl 却能拿到 200 + 正文 ⇒
> **是浏览器这一层被拦**，所以分"只有浏览器连不上 / 两种通道都不通"。

**这个框架被自己的预检数据打掉了。** 新加的诊断列跑出来是：

```
r02 https://movie.douban.com/top250  也不通（URLError: SSL: UNEXPECTED_EOF...）
r09 https://so.eastmoney.com/         也不通（URLError: SSL: UNEXPECTED_EOF...）
```

—— 标准库 `urllib` **也**连不上豆瓣，而它不是浏览器。

于是回头把三条通道**逐站重扫了一遍**，才看清真正的分层：

| 客户端 | TLS 栈 | 豆瓣 | 东方财富 | 微博 / 当当 | 12306 |
|---|---|---|---|---|---|
| chromium | BoringSSL | `ERR_CONNECTION_CLOSED` | ✗ | ✗ | ✗ |
| Python urllib | OpenSSL | `SSL: UNEXPECTED_EOF` | ✗ | ✗ | ✗ |
| curl | **schannel** | **200 / 64416 B** | **200 / 13324 B** | 302（有响应） | 000 |

**区分点不是"浏览器 vs 非浏览器"，是 TLS 栈。**
只有 Windows 自带 schannel 的那个客户端能过；BoringSSL 和 OpenSSL 都过不去。
也就是说出口链路对"谁在连"按 **TLS 实现**做了区分 —— 这是本机中间设备/
安全软件那一层的特征，不是站点的问题。

（顺带一个教训：我第一次测 curl 时用 `-o /dev/null`，`-w size=0` 让我
以为"curl 也只拿到 0 字节"，差点把结论写成"连 curl 都不通"。
换成写真实文件再量字节数，才看到 64416 B。**量字节数要落到真实文件，
别信 `-o /dev/null` 的 size_download。**）

## 5.4 所以工具改成"两条通道"：urllib + curl

单看 urllib 会把豆瓣/东方财富误判成"站点/网络问题"（实际站点是好的）。
改成两条通道后，结论才是对的：

- **有任一通道连通** → 站点是好的；浏览器连不上是**出口在区分客户端**，
  换机器/换客户端就好（豆瓣、东方财富、微博、当当、B 站都落这里）；
- **两条都不通** → 疑似站点/网络问题，换网络再测（12306 落这里）。

## 5.5 已排除的解释（都做过对照）

| 假设 | 验证方式 | 结论 |
|---|---|---|
| 沙箱造成的 | 同一脚本沙箱内 / 沙箱外各跑一次 | ❌ 两次完全一样 |
| IPv6 解析问题 | `nslookup`：只有 A 记录、无 AAAA；`curl -4` 得 200 | ❌ 排除 |
| 代理能救 | 直连 5/12 vs 走代理 5/12，失败站点相同 | ❌ 无改善 |
| 站点挂了 | curl 拿到 200 + 真实正文（64 KB） | ❌ 排除 |

## 5.6 数字口径

- 5.1 的修复**不改变**今天的可达数（5/12 → 5/12）：两个通道在这批站上
  碰巧同结论。**它的价值是把一个会撒谎的闸门修正了，不是提分。**
  修复和提升是两件事，要分开说。
- 真实站点集 12 个里能进成功率分母的更少（本次 3 个）——
  这一层的结论只能当**环境诊断**看，不能当"Agent 在真实站点上的能力"看。
- 「换机器就好了」是**推断**，不是实测：本机只有这一台可测。
  写在这里是为了给下一步指路，不是下结论。

## 5.7 一句话教训

**环境不可达这个判断，口径必须只有一处，而且不能只有一个客户端。**
判断本身要是不可信，预检就不是在保护结论，而是在替结论打掩护 ——
"7 个站跑不了"可以被记成"环境问题"，也可以被记成"我根本没跑"，
两者的区别全在预检这一层握没握住。

# 实验 7：模型层消融 —— 把"骨架缺陷"和"模型缺陷"分开

## 7.0 为什么做这个，而不是接着改代码

实验 4 留下的状态是：基线 `15/18`，`pass@3 6/6` 但 `pass^3 3/6`。
三条偶发失败（t04 / t05 / t06）都表现成"原地打转熔断"。

按 **§"改完代码基线不动就是归因错了"** 的规矩，在继续改引擎之前，
得先回答一个问题：**这三条到底是引擎不行，还是模型太笨？**

最便宜的分辨手段是**只换模型**：同一套任务、同一份代码、同样跑 3 轮。

```
# 环境变量覆盖 .env（load_dotenv 默认不覆盖已有环境变量，不会弄脏配置）
LLM_MODEL="deepseek-ai/DeepSeek-V3.2" python eval/run_eval.py --repeat 3
```

未改任何任务、未改任何代码。

## 7.1 数字

| 指标 | 7B（`Qwen/Qwen2.5-7B-Instruct`） | 强模型（`deepseek-ai/DeepSeek-V3.2`） |
|---|---|---|
| 按次成功率 | 15/18 = 83.3% | **17/18 = 94.4%** |
| `pass@3` | 100% | 100% |
| **`pass^3`** | **3/6** | **5/6** |
| normal 成功率 | 83.3% | **100%** |
| counter 成功率 | 83.3% | 83.3% |
| 平均步数 | 7.17 | **5.89** |
| 平均 token | 16186.5 | **14518.8** |
| 平均耗时 | 33.6 秒 | 134.6 秒（**慢 4 倍**） |
| 结论带页面证据 | 11/18（1 条被退回重做） | 12/18（0 条被退回） |

逐任务：

| ID | 7B | 强模型 | 结论 |
|---|---|---|---|
| t01 / t02 / t03 | 3/3 | 3/3 | 都稳 |
| **t04** | 2/3 | **3/3** | 偶发失败 → **模型能力** |
| **t05** | 2/3 | **3/3** | 偶发失败 → **模型能力** |
| **t06** | 2/3 | 2/3 | **两边都偶发失败，且形态不同** → 见 7.2 |

## 7.2 ⭐ 消融最大的回报：它暴露了一个**骨架**缺陷

强模型那唯一一次失败（t06 第 1 轮）长这样：

```
steps=20  finished=False  error=达到最大步数上限（20），任务未完成
每一步 ok=True —— 没有任何报错、没有失败重试
20 步里 13 次 scroll，dy 依次：
-200 / -1000 / -500 / -2000 / -3000 / +2000 / -3000 / -5000 / -1000 / -10000 / -5000 …
```

**熔断器一次都没触发。** 原因是动作指纹：

```python
return f"scroll#{action.dy}"      # ← 把滚动量写进了指纹
```

—— 于是"改个滚动量"就等于换了一个**新动作**，`trail.count(sig)` 永远到不了 5。
熔断器被**参数变化**绕过去了，20 步全烧完，任务还是没完成。

这条不是想出来的，是跑出来的：**它只在"模型足够活跃、会自己换滚动量"时才出现** ——
7B 那边是"点同一个按钮 5 次"（熔断生效），强模型这边是"滚 13 次每次不一样"（熔断失效）。

修法：`scroll` 的指纹只保留**方向**（`scroll#down` / `scroll#up`），丢掉幅度。
为什么保留方向：反复滚动本身就是"没有进展"的形态，不需要靠"滚了多远"区分；
但"向下找内容 / 再向上回看"是合理动作，方向得分开。

## 7.3 这条修复的"代价"—— ⚠️ 我当时量错了，结论已收回

我当时的原话：

| 对象 | 结果 |
|---|---|
| 18 次**基线**轨迹离线复算（旧签名 vs 新签名） | 只有那 **3 次本来就熔断失败**的运行会被命中，熔断点完全相同（18 / 18 / 17）——**没有任何一次通过的运行受影响** |
| 强模型 t06 那次真实轨迹 | 旧规则熔断点 = **从不存在**（所以白烧 20 步）；新规则 = **第 7 步** |

**右边那一列的第一个结论是错的，我现在把它划掉。** 理由不是"后来又跑出了别的数"，
而是这个推断**在方法上就不成立**：

> 离线复算只能回答"**旧轨迹**会不会提前熔断"，
> 回答不了"警告改变了模型行为之后，它会走出一条什么样的**新轨迹**"。
> 拿一个不存在的未来去证明改动安全，是自欺。

代价来得很快：这条修复一上线就跑了真基线，**t04 从 2/3 掉到 0/3**。
完整的追查与最终修法见**实验 8**。

⚠️ 另外这句也仍然成立、且这次同样适用：**它把"白烧 13 步"变成"第 7 步明确熔断"，
并没有让 t06 变通过。** 熔断仍然是熔断，只是更早、更便宜、更显形。

这和实验 4 第 ③ 节是同一个教训的第二次出现：
**"加了一个机制" ≠ "解决了那条任务"**。要判断 t06 能不能过，
得在新规则下真跑一次 —— 这一步还没做。

## 7.4 这组数字怎么讲才不算吹

- **`17/18` 不能说成"项目成功率 94%"**：分母是 18 次运行 / 6 个任务，
  而且任务集是自建的玩具站任务（`quotes` / `books.toscrape.com` / `bing`）。
- 真正的信息量在**两个模型之间的差分**上：
  `pass^3 3/6 → 5/6` 说的是"t04、t05 的偶发失败主要来自模型能力"；
  `t06 两边都是 2/3` 说的是"这条两边都栽，更像骨架问题"。
  **没有这个差分，光看 `17/18` 只会得出"换个贵模型就好了"这种没用的结论。**
- **成本栏不能横比**：两次跑的"平均成本 ¥0.02"是用**同一套单价**
  算出来的，而 7B 和 V3.2 的实际单价差很多。要看钱得按各自的价目表重算 ——
  这个数现在只能用来做"同模型内不同版本"的对比。
- 强模型**慢 4 倍**（33.6s → 134.6s），其中 t06 那一次烧了 **576 秒**。
  换模型不是免费的：它是用时间换稳定性，而那条 576 秒恰恰是被骨架漏洞放大的。

# 实验 8：把"原地打转"这条 bug 真正修掉（以及一次被自己打脸的复算）

## 8.0 起因

实验 7 的结论是"熔断器被参数变化绕过去了，改成方向签名后第 7 步就能熔断"，
并且留了一句"要判断 t06 能不能过，得在新规则下真跑一次 —— **这一步还没做**"。

这一节就是去把没做的那一步做了。结果是：**那条修复一上线就把 t04 打坏了。**

## 8.1 事故：基线从 15/18 掉到 14/18，t04 从 2/3 掉到 0/3

改完 scroll 指纹（`scroll#{dy}` → `scroll#方向`）立刻跑真基线：

| 任务 | 改之前 | 改之后 |
|---|---|---|
| t01 / t02 / t03 | 3/3 · 3/3 · 3/3 | 3/3 · 3/3 · 3/3 |
| **t04** | **2/3** | **0/3** |
| t05 / t06 | 2/3 · 2/3 | 3/3 · 2/3 |
| 合计 | 15/18 | 14/18 |

三条 t04 全灭，熔断日志长这样：

```
检测到原地打转：动作 scroll#up 累计出现 5 次（其中末尾连续 1 次）且无进展，已熔断
```

**"末尾连续 1 次"**。这句话本身就是判决书：t04 的 5 次滚动分散在第
4 / 6 / 11 / 12 / 14 步，每一步之间它都在获得新信息（点搜索结果、翻页、读正文），
却被"**整轮累计** 5 次"判成了原地打转。

> 顺带说明：这个"累计 vs 连续"的措辞不一致，实验 4 那会儿就发现了
> （`loop_counts` 的注释里留着当时的实测）。当时**故意只修措辞、不动判据**，
> 理由是"改判据会动基线数字，必须单独立项"。
> 现在立了项，结论是：**不光措辞错，判据本身也错。**

## 8.2 判据错在哪：把"页面"的属性算成了"动作"的属性

原地打转的定义是"**没有获得新信息**"。这是**页面**的属性，不是动作的属性。
用"某个动作整轮出现过几次"去近似它，必然两头不讨好：

| 失效形态 | 例子 | 累计判据的表现 |
|---|---|---|
| **误杀** | t04：5 次滚动分散在 14 步里，中间都在获得新信息 | 判成"累计 5 次"→ 熔断（错） |
| **漏判** | 强模型 t06：13 次滚动，每次 dy 都不同 | 指纹各异 → 永远不触发（错） |

所以修法不是调阈值，是**换判据**。分三刀。

## 8.3 第一刀：判据从"累计"改成"连续"

只杀**真的连着重复**的动作。t04 的 5 次滚动末尾连续只有 1 次 → 不再命中；
强模型 t06 那种交替方向的滚动也照样漏（这点后面承认了）。
两个引擎同步改，测试 `test_fuse_decision_now_uses_consecutive` 钉住。

**这一刀是"少犯错"，不是"多抓人"。**

## 8.4 第二刀：加"页面指纹"判据 —— 而且元素清单必须剔除

动作指纹只管"同一个动作连着重复"，对"换着花样滚"完全无感。补一套**页面**判据：
把一帧页面压成短哈希，连续几帧一字未变 = 真的没收获。

第一版指纹放的是 `url + title + 元素清单 + 正文`，直觉是"结构变了 = 有新信息"。
**量了一遍才发现是错的**，写了个不调模型的探针
（`scripts/probe_page_fp.py`），真浏览器上连滑 4 次再连滑 4 次：

```
动作            指纹              元素数   正文长
goto            533ea144404caad5     85     2029
scroll +500     533ea144404caad5     85     2029
scroll +500     56f43498c80d1490     85     2029
scroll +500     1aaa2f57c2b72731     77     2029
scroll +500     34d279a4bc2bcffd     71     2029
scroll -500     b12911403fe18644     85     2029
scroll -500     533ea144404caad5     85     2029   ← 滑回原位，指纹原样回来了
```

**正文全程 2029 字一字未变**，抖动全部来自元素数（85 → 77 → 71）。
原因是感知层采集元素时带**视口过滤**（`r.bottom < -800` 才丢弃，
见 `perception.py` 的 `visible`）—— 滚动会让页面顶部的元素掉出采集范围。

也就是说这个抖动纯粹是"我站在哪儿看"，**不是"页面上多了什么"**。
带着它做停滞检测的后果很讽刺：**"滚动打转"这一类恰好检测不到**
（每次滑指纹都变，计数器永远清零）—— 而那正是这个机制要抓的主要形态。
一个在自己目标场景上失灵的判据，比没有更糟：它会让日志显得"检查过了"。

修法：指纹只留 `url + title + 正文`。**口径也自洽了** —— "有没有新信息"
等价于"模型能读到的东西有没有变"，而正文正是它唯一的信息来源。

## 8.5 第三刀：收束期**拦住动作**，不能只喊话

停滞触顶之后不直接熔断，而是先注入一段强指令逼模型给结论。
理由是判分口径：反例任务的合格标准是"**主动说出来**"，硬熔断不算拒答
（`eval/run_eval.py` 的 `judge()` 里写着 `熔断不算拒答`）。

**第一版只"喊话"——数够步数就熔断。实测证明没用。**

我把 t06 的一次真实失败的动作序列重放了一遍
（`scripts/probe_replay_stall.py`，不调模型，纯重放 + 逐帧算指纹）：

```
  步 动作             指纹             停滞  事件
  9 scroll#600     4ed08c4b5b22deb1    1
 10 scroll#600     4ed08c4b5b22deb1    2
 11 click#27       4ed08c4b5b22deb1    3  → 警告
 12 scroll#600     4ed08c4b5b22deb1    4  → 警告
 13 click#27       4ed08c4b5b22deb1    5  → 警告
 14 extract        4ed08c4b5b22deb1    6  → 收束（逼 finish）
 15 extract        4ed08c4b5b22deb1    6  → 收束（逼 finish）
 16 click#1        4ed08c4b5b22deb1    6  → 收束（逼 finish）
 17 click#28       6e69a9fa159795d6    0   ← 换了个页面，计数器清零
```

**收束指令确实在第 14 步注入了**，模型回手就是 `extract` / `extract` / `click#1`，
把指令当耳旁风，一直磨到步数上限。而且第 17 步换页又把计数清零，
等于给了它一轮"新额度"。

修法两处：
1. 收束期间的任何非 finish 动作**不执行**，只回一条明确的拒绝；
   拒绝累积到 `CLOSING_MAX_STEPS` 才熔断。这样"预算"数的是**模型拒答的次数**，
   而不是引擎干等的步数。
2. 收束预算**不随换页清零**（换页只退出收束状态，不清零已用的额度）。

> **为什么不干脆替模型写结论。** 认真考虑过，放弃了：反例任务考的就是
> "识别并声明做不到"，引擎代写等于把判分口径改了 —— 数字会变好看，
> 但它不再说明模型有能力。而且 t04 的 `must_contain` 是空的，
> 一句引擎代写的"无法获取"会**误判成通过**。本项目的底线是假阳性比假阴性更该防
> （见实验 4 之后那段），所以到这里为止。

## 8.6 ⭐ 顺手做出来的三件观测工具（这才是本轮最值钱的东西）

排查过程暴露了一个**观测盲区**：`trace.json` 里只有动作和结果、**没有页面**。
明明看见 Agent 在原地打转，却没有任何字段能回答"当时页面到底变没变"，
最后只能另写脚本把动作序列重放一遍才量出来。

补上：

| 产物 | 作用 |
|---|---|
| `StepRecord.page_fp` / `.stall_count` | 每步的页面指纹与停滞计数落进 trace，**读就行**，不用再重放 |
| `scripts/probe_page_fp.py` | 不调模型：量"滚动到底改不改指纹"（8.4 的结论就是它测出来的） |
| `scripts/probe_replay_stall.py` | 不调模型：重放一次真实运行的动作序列，逐步打印指纹与停滞（8.5 的证据） |
| `scripts/analyze_stall_rules.py` | 不调模型：拿已落盘的指纹序列**离线对比两种判据**（8.7） |

## 8.7 用数据选判据，而不是靠口味

停滞判据有两种自然写法，都说得通：

| 判据 | 规则 |
|---|---|
| **A. 同页连续** | 相邻两帧指纹相同就 +1，变了清零 |
| **B. 未见新页** | 当前指纹"以前出现过"就 +1，没见过就清零 |

B 看着更强（能抓住"在两个已知页面之间来回跳"这类交替循环，A 抓不住）。
但把它拿已落盘的指纹序列算一遍（阈值 6）：

```
                            步  完成     A最大  A首次触发   B最大  B首次触发
20260921-230335-t04         20  未过       6       20      6       20
20260921-230842-t06         20  未过       2        -      6       20
20260921-231051-t04         20  未过      12       14     12       14
20260921-231205-t05         17  通过       5        -      6       17   ← B 会喊停
规则 A 触发 3/13；其中本来通过的有 1 次
规则 B 触发 6/13；其中本来通过的有 2 次
```

两条结论都很硬：

1. **B 救不了 t06**：它也要等到**第 20 步**才够阈值 —— 而 `MAX_STEPS` 就是 20，
   等于没机会。
2. **B 的误伤候选更多**：会在一次**通过**的 t05 运行里就喊停。

所以选 A。**这不是口味，是算出来的。**

> ⚠️ 这个脚本的口径必须说清：它只回答"**这段已经落盘的指纹序列会不会触发**"
> —— 那是个纯函数，没有不确定性。它**不**回答"触发之后模型会怎样"。
> 上一轮（7.3）就是拿"旧轨迹重算"去证明"改动没有副作用"，然后被真基线打脸。
> 所以它的结论只能用来**排除明显更差的规则**，不能用来宣称"改了会更好"。

- 结论：**判据的语义修对了，机制是真的在动（trace 里逐帧可见），
  但没有让总分变好。** "加了一个机制"≠"解决了那条任务" ——
  这已经是本项目第三次撞上同一句话（实验 4 第 ③ 节、实验 7.3、本节）。

## 8.9 ⭐⭐ 顺着审计表挖出来的真瓶颈：步数预算，不是熔断器

8.8.1 那张表里有个数字很扎眼：**t05/t06 的 9 次失败全部是"步数上限耗尽"**，
而它们通过的那几次用的是 15~19 步。也就是说 **`MAX_STEPS=20` 恰好卡在收敛边界上**。

这是个可以直接验的假设。同一套代码、同一个模型，只把预算放到 30：

```bash
python eval/run_eval.py --only t04 t05 t06 --repeat 4 --max-steps 30
```

| 任务 | 预算 20 | **预算 30** |
|---|---|---|
| t04 | 2/4 | **4/4** |
| t05 | 1/4 | **2/4** |
| t06 | 1/4 | **4/4** |
| **合计** | **4/12 = 33%** | **10/12 = 83%** |

而且看通过时用了多少步 —— **t06 那三次是 21 / 23 / 25 步，全部超过老的 20 上限**。
换句话说：那三次在旧预算下**注定失败**，不是因为模型做不到，是因为预算用完了。

**结论：这几条任务的主要瓶颈是步数预算。** 这也顺带修正了实验 7 的一个判断 ——
当时看到"7B 和强模型在 t06 上都是 2/3"，推断"两边都栽 ⇒ 更像骨架问题"。
方向是对的（确实是引擎侧的问题），但**定位错了**：不是熔断器不够强，
是预算太紧。

### 动了什么、以及为什么这不叫"挪尺子"

`MAX_STEPS` 默认值 20 → **30**（`src/bagent/config.py`，`.env.example` 同步）。

必须把这条界线讲清楚，否则这个改动就是可疑的：

| | 判分参数 | **产品参数** |
|---|---|---|
| 例子 | `must_contain`、拒答措辞、`kind` | `MAX_STEPS`、超时、并发 |
| 动了会怎样 | **口径变了**，前后数字不可比 | 口径不变，但**成本变了** |

`MAX_STEPS` 属于后者：它回答的是"这个 Agent 愿意为一个任务花多少步"，
是产品取舍，不是判分口径。改它不违规 —— 但**必须把代价和前后数字都写出来**：

| | 预算 20 | 预算 30 |
|---|---|---|
| 失败任务的成本 | 20 步就停 | 可能烧到 30 步 |
| 平均耗时（三条难任务） | 100 秒 | 75 秒（**反而更低**：早点成功就早停） |
| t06 通过步数 | —（4 次里 3 次失败） | 21 / 23 / 25 |

> 注意一个反直觉的点：**加预算之后平均耗时反而降了**。
> 因为失败的运行是"烧满预算"的，成功的运行是"做完了就停" ——
> 把一批注定烧满的失败变成中途成功，总账是省时间的。

⚠️ **跨版本对比的红线**：本项目早先的 `15/18`、`14/18`、`13/18` 三组基线
**都是 `MAX_STEPS=20` 下跑的**，和 30 下的数字不能直接比。
所以评测脚本也一并改了 —— 现在**步数预算会打进报告头部和每一条明细**
（`eval/run_eval.py` 的 `max_steps` 字段），和 `model` 字段同等对待。
规则是：**凡是会改变结论的参数，都必须跟着数字一起走。**

### 为什么不用"按有没有进展动态延长预算"

因为停滞检测已经在做类似的事：真卡住的运行会被提前熔断（8.7 那条 t04 就是），
不需要靠预算兜底。而 t05/t06 那种"每一步都在换页面、就是不给结论"的形态，
判据上**不构成停滞**（实测最大停滞计数只有 1~4，阈值是 6）——
动态延长对它无效，只有直接加预算有效。

## 8.12 ⭐ 一次"看起来参数是对的"：预算被 `.env` 静默按在 20

### 8.12.0 发生了什么

8.9 把 `max_steps` 的代码默认值从 20 改成 30 之后，按计划重跑完整基线做验证。
跑了 8 分 45 秒，翻开轨迹，最后一行是：

```
达到最大步数上限（20），任务未完成
```

**预算还是 20。** 而报告头部打印的也是"步数预算 20"—— 一切看起来都正常。
原因是 `.env` 里那句遗留的 `MAX_STEPS=20` 覆盖了代码默认值。

也就是说："我改了代码"和"实际生效的值"之间隔着一个**看不见的覆盖**，
改与不改，从报告上完全看不出区别。差一点就把这份 20 预算下的基线当成 30 的
报出去，并把"数字没变"读成"这次修复没用"。

**最值得记的一点**：8.9 的注释里早就写下了这条警告
（"跨版本对比时必须对齐预算"）—— 但警告写下来了，没有任何东西替你检查。
写下来的警告不构成防线。

### 8.12.1 修法：让"来源"成为可打印、可落盘的事实

| 改动 | 作用 |
|---|---|
| `config.resolve_int(name, default) -> (生效值, 来源)` | 来源三种：进程环境变量 > `.env` 文件 > 代码默认值 |
| `MAX_STEPS_DEFAULT` 抽成模块常量 | 原先这个数写在三个地方（`Settings` 的 `default_factory`、`.env`、`.env.example`），漂移的口子就是它给的 |
| 头部改打 `步数预算 30（来自 .env 文件）` | 与代码默认值**不同**时额外黄字警告"跨版本对比必须对齐这一档" |
| 报告顶层加 `max_steps` / `max_steps_source` / `max_steps_default` | 两份 `eval_*.json` 对比时第一眼看清是不是同一档 |

要分清"真环境变量"和"`.env` 文件"，必须在 `load_dotenv()` **之前**快照
`os.environ`（它默认不覆盖已存在的变量，加载之后两者就分不清了），
另外用 `dotenv_values()` 单独读一次 .env。实测两者确实能分开。

值存在但解析不出来（`MAX_STEPS=abc`）时，生效值退回默认，但来源照实写成
"不可解析，已回退默认值" —— 不让写坏的值看起来像生效了。

### 8.12.2 顺带核实掉的一个疑点（不是 bug）

`runs/eval_20260921-23*.json` 里每条明细都没有 `max_steps` 字段，
一度以为是落盘时被过滤掉了。查 `git show db59baf:eval/run_eval.py` 才知道：
那个字段**是 e983e2f 才加进 `run_task` 返回体的**，那几份 JSON 只是早于它。

**但由此暴露出一个诚实问题**：8.9 里那两组关键数字（高阶任务 4/12 与 10/12）
的预算**只存在于当时的终端输出里**，文件里复核不了。也就是说这条
"预算 20 → 30 让 4/12 变 10/12"的结论，在此刻无法从留档数据中重算。
如实记下，不假装可复核 —— 从 e983e2f 起每条明细与会话顶层都带预算，往后没这个问题。

### 8.12.3 教训

> **把参数值打印出来 ≠ 参数是对的。**

## 8.13 ⭐ t04 动作层的真实形态：不是"提交按钮超时"

### 8.13.0 先把上一版的三处说法收回

8.10 的上一版把 t04 写成"必应首页 `click` 提交按钮**稳定超时**，三次里只有
一次按了 Enter，URL 从头到尾停在 `cn.bing.com/`；该查超时值（**3000ms 可能偏短**）"。
把 30 条 t04 轨迹翻完之后，这句话**三处都不准**：

| 原说法 | 实测 |
|---|---|
| 提交按钮稳定超时 | 超时的目标不是提交按钮，是**必应首页「热点资讯」的新闻标题**（`<a title="钟南山团队发现肺结节新趋势">`）和**已隐藏的菜单项** |
| 超时值 3000ms，可能偏短 | 实际 `STEP_TIMEOUT_SECONDS=30`，即 **30 秒**（报错原文 `Timeout 30000ms exceeded`）。不是太短，是**太长** —— 每次失败白等 30 秒 |
| 是推理/提示词问题 | 有一部分是，但**观测层的问题更直接**（见 8.13.2） |

### 8.13.1 数字：输入搜索词之后，模型干了什么

30 条 t04 轨迹（`runs/*t04/trace.json`；其中 29 条来自 9/19~9/21 的历史运行，
1 条是 8.12 那次跑在错误预算上的），统计"输入搜索词之后的第一个动作"：

| 输入之后的动作 | 次数 | 结果 |
|---|---|---|
| `press Enter` | 7 | **7/7 全成功** |
| `click` 某个 ref | 12 | 8 成功 / **4 超时** |
| `extract`（先读页面再定） | 9 | 全部成功 |
| 动作输出不合法（`ref` 不是整数） | 2 | 白费一步 |

**按 Enter 的 7 次一次没失手。** 缺口是模型只有约四分之一的时候去按 Enter。

### 8.13.2 点不动的是什么，以及为什么喂回去的报错没用

三条真实报错（原样摘录）：

```
locator resolved to <a target="_blank" data-ba-ref="21"
    title="钟南山团队发现肺结节新趋势" data-h="ID=...

locator resolved to <li id="academic" role="menuitem" data-ba-ref="9"
    class="scope try_exp...

Locator.scroll_into_view_if_needed: Timeout 29994ms exceeded.
  - attempting scroll into view action
    2 × waiting for element to be stable
      - element is not visible
```

注意第一行：**`locator resolved to`** —— 元素在 DOM 里，找到它了，但点不动。
`ref=21` 是必应首页资讯流里的**新闻标题**。这类元素在**持续轮播**，
而 Playwright 点击前要等元素"稳定"（相邻两帧包围盒不变），
**轮播元素永远等不到**，于是耗满 30 秒。

第三条的 `element is not visible` 是另一种：感知时可见、点击时已隐藏的菜单项。

而喂回给模型的报错是 Playwright **原样透出的多行 call log** ——
模型读不出"这个目标永久点不动、换条路"，只能重试。轨迹里能看到它
连着三步点同一个 `ref=9`（第 15/16/17 步），三步就是 90 秒。

代价是实打实的：单次失败的 t04 跑了 **397 秒**（20 步）。

### 8.13.3 定位：观测层 + 动作层

- **观测层**：`_COLLECT_JS` 的 `visible()` 只判断"此刻可见、有尺寸"，
  判断不了"点得动"（轮播中的元素此刻确实有尺寸、确实"可见"）。
  `label()` 对空标签元素只能给出空串，元素清单里因此混着一批 `「」` 项，
  模型无从分辨哪个才是"搜索"。
- **动作层**：`_click` 让 Playwright 的异常原样上抛，报错对模型不可操作。

> **教训：报错文本是给模型看的，不是给人看的。**
> 把库的原始异常直接透进 prompt，等于把"排查"这件事推给了模型 ——
> 而它既看不到 DOM，也没有 Playwright 的语义知识。

### 8.14.2 ⭐ 更要紧的：t06 的失败形态**加预算治不了**

两条 t06 失败都写「达到最大步数上限（30）」，但翻开轨迹看形态 ——

```

 8 click [28]「Add to basket」        16 click [1]「Books to Scrape」
12 click [ 1]「Books to Scrape」      19 click [2]「Home」

…一路循环：详情页 ↔ 目录页，反复"加入购物车"，从不收尾
```

**停滞计数全程只有 0~2（阈值是 6）。** 因为页面每步都在变
（A→B→A→B，每一帧都和上一帧不同），`page_fingerprint` 判不出"没有进展"。

这正是 8.2 里预判过的那个漏洞，原文写着：

> 必然一边漏（交替滚动 / **交替跳页**绕过去）一边误杀（分散但正常的探索）。

当时的对策是先修"误杀"、把"漏"记在账上。现在账面到期了：**t06 就是那个"漏"。**

所以 8.9 那条推断（"9 次失败全是步数上限耗尽 ⇒ 瓶颈是预算"）
**观察是对的、因果是错的**：它们确实都死于步数上限，但**加预算并没有解决它** ——
真实原因是没有一条判据能让它停下来。t06 需要的是**识别振荡**
（例如"同一对页面之间来回超过 N 次、且每次都确认过没有目标功能，就必须 finish"），
而不是更多步数。这也反过来解释了 8.9 里那件当时想不通的事：
"为什么动态延长预算对 t05/t06 无效" —— 因为问题从来不在"给多少步"。

### 8.14.3 顺带挖出的第二个真缺陷：`ref` 与 `dy` 字段被写混

这次基线里三条失败运行**都在第 20 步**撞上同一个动作解析错误。原文：

```
模型输出不是合法 JSON：动作字段不合法:
  [{'type': 'int_parsing', 'loc': ('ref',), 'input': 'dy=500', ...}]   # 把 dy 写进了 ref
  [{'type': 'int_parsing', 'loc': ('ref',), 'input': 'None',   ...}]   # 想表达"没有 ref"
```

t02 那次更贵：第 6 / 19 / 20 / 21 步**连续犯**，触发「模型连续输出非法格式」
提前中止 —— **21 步全部作废**。

两个都算不上"模型太笨"，是可修的工程口子，但**改法不同**：

- `"None"` / `"null"` / `""` 表示"这个字段没有值" —— **无歧义**，应当接受；
- `"dy=500"` 是**字段写混**，但**不该猜**：猜成"滚动 500 像素"等于替模型
  做了语义决定，可能执行一个它根本没打算做的动作。正确做法是
  **把话说清楚**（报错直接点明"你把 `dy` 写进了 `ref`"，让它自己改）。

⚠️ **两条都不许当成"已验证有效"**：修完必须单独量边际效果（见技能第五条）。
另外 `raw_action` 存的是 `"(格式错误)"` —— 模型**原始输出没有留档**，
这次只能靠 pydantic 的 `input` 字段倒推。这是观测缺口，一并记下。

### 8.14.4 这一轮真正的收获

不是"数字变好了"（**14/18，和预算 20 下的 14/18 相同**），而是：

1. **一个被高估的结论被自己的基线打回来了** —— 4/4 是运气，5/7 才是水平。
   这正是"3 轮分不出 13 和 14"那句话要防的事，这次它真的发生了。
2. **一个"加预算"的归因被证伪，真因浮出来**：t06 是振荡，不是步数不够。
3. **一个可修的工程口子被量化**：`ref` 字段解析，最贵一次白烧 21 步。

## 8.15 ⭐ 振荡判据：加了一条，然后被一次"假成功"拦住

### 8.15.0 起因

8.14.2 已经定位到 t06 的失败形态是**振荡**：模型在书籍站的详情页与目录页之间
来回走满 30 步、反复点「Add to basket」，而两套已有判据全都看不见它：

| 判据 | 看什么 | 为什么漏掉振荡 |
|---|---|---|
| 动作指纹 | 行为有没有重复 | 振荡时动作是**交替**的（详情页 / 加购 / 详情页 / …），任何单个动作的连续次数都停在 1 |
| 停滞检测 | 页面有没有变 | 振荡时页面**每步都在变**（A→B→A→B），实测停滞计数全程只有 0~2（阈值 6），**一次警告都没注入过** |

所以这一轮补第三套判据。

### 8.15.1 判据：`oscillation_pages`（`src/bagent/agent.py`）

最近 `window=4` 步里，如果

1. 窗口内**没有出现以前没见过的页面**（出现了 = 有进展），且
2. 窗口内不同页面数**恰好落在 [2, 2]**

就判定"在已经去过的一小片页面之间来回走"。

两个条件缺一不可，都是**实测调出来的**：

- 光"重走同一条边"不够 —— 必应"首页 → 结果页"的正常往返也满足它（那种往返
  每轮都在拿新结果），加"窗口内无新页面"能把这类误触压掉一部分；
- 下界 2 是**刻意**的：窗口里只有同一个页面时那是"页面一字未变"，归
  `update_stall` 管。两套机制各管一半，是互补不是重复。

### 8.15.2 为什么只发警告、不熔断

离线在**已落盘轨迹**上比过七组候选判据、每组再扫 n/w 参数
（`scripts/choose_oscillation_rule.py`，它替换掉原先三份一次性的探查脚本）。
结果：

    最好的一组 D(n=3, w=4) —— 重走同一条边 >= 3 次
      受害运行（耗尽预算/熔断）   19/19   全抓到
      已收敛的运行               29/62   也触发，其中 11 条是 normal
                                 （主要是 t04 必应"首页 <-> 结果页"的正常往返）

**该抓的一个不漏，但不该抓的也误伤近一半。** 这种判据拿去熔断，等于用
"打死 11 条正常任务"换"抓住全部受害任务"。所以它不进熔断，只进提示词。

口径：轨迹数会随跑测增长，上面是 2026-09-22 的快照，复算用那个脚本。
而且它只回答"这段序列会不会触发"，回答不了"触发之后模型会怎么走" ——
所以它只能用来**筛掉明显分不开的规则**，选出来的仍必须真跑。

### 8.15.3 ⚠️ 第一次跑出 12/12 —— 而那个数字是假的

改动后第一轮基线（`--only t04 t05 t06 --repeat 4`，预算 30）：

    对照（改前）   8/12    t04 4/4   t05 2/4   t06 2/4
    改动后        12/12    t04 4/4   t05 4/4   t06 4/4

看着像一次干净的胜利。**但同一份报告里有个数对不上**：`结论带页面证据`
从 5/12 掉到 1/12。去读答案原文，t04 的四条里有三条是这样：

    这个页面上没有搜索结果
    在必应首页无法找到搜索结果。
    无法找到搜索结果。

t04 是**正常任务**（"读出第一条自然搜索结果的标题"）。它交的是"我没做到"，
而判分把它记成了成功。

### 8.15.4 根因：t04 的判分**从来就只测了"有没有输出"**

`judge()`（`eval/run_eval.py`）的 normal 分支里有这么一条：

```python

    return (True, "已完成") if answer else (False, "完成但结论为空")
```

而 `tasks/examples.json` 里 **t04 的 `must_contain` 是空的**
（t01/t02/t03 都有真锚点，只有它没有）。两条一叠加：
**t04 只要吐出一句非空的话就算过**，"无法找到搜索结果"也算过。

这不是本轮改出来的，是**一直存在**的：改前那一轮 t04 也是 4/4，
只不过它那四条答案恰好都是页面上的真内容（"ReAct 是一种新颖的方法…"、
"重读 ReAct 论文：LLM Agent 的开山之作 - 知乎"）——假阳性没被触发而已。

⚠️ 更刺眼的是：README「判分口径」一节**早就写了**这条规矩
（"`must_contain` 为空 ⇒ 任何非空答案都算过"），但 t04 始终没落实锚点。
**规矩写进了文档，没写进任务文件。**

### 8.15.5 ⚠️ 我的第一个归因，被自己的轨迹推翻了

第一版注入的警告是这样结尾的：

    …请立刻换一个明显不同的做法；如果已经确认这件事做不到，就**直接 finish**，
    在 answer 里写清为什么做不到（**这类结论免检 evidence**，不需要引用不存在的东西）。

第一眼看上去这**就是**原因："免检 evidence"被当成奖励发在了循环里，
模型在 t04 上一收到提醒就去交差 —— 绕圈子只说明没走对路，**不等于任务做不到**，
而我把这两件事写成了同一件事。于是把它改掉了：

    ⚠ 但别把「绕圈子」当成「做不到」：**「我还没找到」不等于「页面上没有」**。
    来回走只说明你没走对路。只有当你已经站在正确的页面上、确实确认过这件事无法完成，
    才把结论写成「做不到」；否则先换做法。

（免检规则本身没错 —— 反例任务确实没法逐字引用一个不存在的东西 —— 它仍然写在
`SYSTEM_PROMPT` 的 evidence 一节里，只是不该在循环里再当胡萝卜发一遍。）

**但改完还要验，验的结果把上面这套说法推翻了。**

给 `StepRecord` 加上 `osc_pages`（8.15.7）之后，可以直接读 trace 回答
"这次运行到底有没有被提醒过"，不用再重放。修正后那一轮（`eval_20260922-101659.json`）：

| t04 结果 | 步数 | 注入过警告？ |
|---|---|---|
| 通过 | 19 | **有**（第 8、11 步）|
| 失败 | 18 | **无** |
| 失败 | 15 | **无** |
| 通过 | 6  | 无 |

**两次失败一次警告都没收到**，而**收到警告的那次照样答对了**。
所以"免检胡萝卜把模型推向拒答"这个机制**不成立**。
（回头用同一个办法核第一轮：那三条拒答的 t04 里，能查到的也都没有注入 —— 见 8.15.3 的脚本。）

改掉那段措辞仍然是对的（循环里不该发"免检通行证"），但它**不是** t04 退化的原因。
这就是为什么要先落盘、再下结论：**一个说得通的故事，和一个被数据支持的故事，
是两件事。**

**目前的头号嫌疑（尚未验证，别当结论）**：`SYSTEM_PROMPT` 里我加的那条
**常驻**规则 ——

    ⚠️「没有新信息」不等于"同一个动作连续重复"。在已经去过的几个页面之间来回走、
    一直没走到新页面，同样是没有新信息 …… 一旦出现就不要再试第二次，直接 finish。
    如果连"做不到"都还没确认清楚，就在 answer 里写清你已经试到哪一步。

它和注入警告不同，是**每一轮都在**的。而 t04 的失败恰恰发生在**没有触发警告**的运行里 ——
那更可能是"常驻措辞"而不是"临时提醒"在起作用。
下一步该做的是**把这条常驻规则收窄、只保留判据说明、去掉"直接 finish"，
然后专门重跑 t04（且把 `--repeat` 提到 6 以上）** —— 而不是现在就改，
n=4 的信号改一次就是往噪声上拟合一次（第 4 节那句"3 轮分不出 13 和 14"说的就是这件事）。

### 8.15.6 判分补一条：正常任务给拒答 = 没完成

加在 `judge()` 的 normal 分支，**放在 `must_contain` 检查之前**
（顺序要紧：反例措辞的答案里往往也夹着关键词）：

```python
if any(m in answer for m in REFUSAL_MARKERS):
    return False, f"正常任务却给了拒答（不是有效结论）: {answer[:40]}"
```

**⚠️ 改判分口径必须先证明对照没被新尺子污染。** 做法是把新规则套回
**已落盘**的两份报告（答案都存进了 `eval_*.json`，是确定性重算）：

    改前那份    8/12 ->  8/12    （它的 t04 答案都是页面真内容，没触发新规则）
    改后那份   12/12 ->  9/12    （3 条 t04 翻成失败）

所以"改前 8/12"仍然可用，A/B 对比成立。

**已知代价**也钉进了测试：拒答判定是子串匹配，正常答案里带"没有"同样会被判失败
（`test_correct_answer_that_mentions_a_refusal_word_is_flagged`）——
这是一处真的假阴性风险，接受它是因为它拦住的是"答不出来却记成成功"。

### 8.15.7 顺手补掉的两个结构性隐患

1. **两个引擎的提示文本合成一份。** 原来 `agent.py` 与 `graph_agent.py` 各抄一份、
   靠注释声明"逐字一致" —— 实测真的漂移了（改了一处忘另一处，没有任何测试会红）。
   现在抽成 `oscillation_warning(pages)` 单一实现，并加源码级断言：
   两个引擎都必须调用它。
2. **观测缺口：`StepRecord.osc_pages`。** trace 里读不回"这一步到底提醒没提醒"
   （那段文本只活在 prompt 的 history 里），验收时只能另写脚本按同一函数重放序列。
   把提醒落盘后，直接读 trace 就有答案。这和当年加 `page_fp` 是**同一个教训**：
   观测不到的东西，事后一定会靠猜。

### 8.15.8 数字（全部按**修正后的判分**重算过）

判分口径改过（8.15.6），所以下面每个数都用同一把尺子量 ——
对照那一轮是用新规则**离线重算**的（答案已落盘，重算是确定性的）：

    python eval/run_eval.py --only t04 t05 t06 --repeat 4     # 预算 30，Qwen2.5-7B

    t04（normal）    对照 4/4  ->  修正后 2/4
    t05（counter）   对照 2/4  ->  修正后 4/4
    t06（counter）   对照 2/4  ->  修正后 4/4
    ──────────────────────────────────────────────
    合计             对照 8/12 ->  修正后 10/12（83.3%）

    修正后那轮：pass@4 100% ｜ pass^4 66.7% ｜ normal 50% ｜ counter 100%
                平均步数 13.58（对照 13.25）

中间还有一轮"旧措辞 + 新判分"，是 9/12（t04 1/4、t05 4/4、t06 4/4）。
**两轮在 t05/t06 上完全一致（都是 4/4），只在 t04 上不同（1/4 与 2/4）。**

**这组数该怎么讲：**

1. **目标达成了，而且复现了。** t06 从 2/4 到 4/4，两轮独立跑测都成立；
   收尾步数从"耗尽 30 步"变成 12~19 步。t05 同步从 2/4 到 4/4。
   也就是说：**"来回跳"这条盲区补上了，反例任务从 4/12 变成 8/8。**
2. **t04 掉了下来，而且原因没查清。** 4/4 → 2/4（两轮合并 3/8）。
   对照 4/4 vs 合并 3/8，Fisher 精确检验 **p≈0.08** —— 够呛说是显著，
   但也**不能当没发生**。更麻烦的是 t04 的分数本来就最不可信（没有锚点，见 8.15.4），
   所以它既可能是真退化，也可能是"以前那个 4/4 本来就虚"。
   **下一步必须先给 t04 补一个真锚点，它的数字才有资格进入结论。**
3. **净 +2，但这不叫"改好了"。** 准确的说法是：
   **振荡提醒修好了它要修的两个任务（counter 4/12 → 8/8），
   代价是 t04 出现了一个尚未归因的退化。**

### 8.15.9 教训

1. **"分数涨了"不等于"变好了"。** 第一轮涨的 4 分里有 3 分是判分假阳性。
   总分是**最后**才该看的东西 —— 先看同一份报告里其它指标有没有对不上
   （这次是"结论带页面证据"从 5/12 掉到 1/12）。
2. **判分口径也是代码，也会假阳性。** 动代码之前先问"这个任务到底在测什么"。
   t04 的答案很直白：它只测了"有没有输出"。
3. **写进文档的规矩不等于执行了的规矩。** "`must_contain` 为空 ⇒ 任何非空答案都算过"
   这条 README 里早就写着，任务文件里始终没落实 —— 于是它原样复发了一次。
4. **一个说得通的归因，也可能被自己的数据推翻。** 8.15.5 那个"免检胡萝卜"的故事
   非常顺，顺到差点直接写进结论；是 `osc_pages` 落盘之后读 trace 才发现：
   两次失败的 t04 **根本没收到过警告**。
   **先让问题可观测，再下因果结论。**
5. **别拿 n=4 的信号反复调提示词。** t04 那 1~2 分的差动，改一次就是往噪声上拟合一次。
   要么把 `--repeat` 提上去，要么先修判分（补锚点）再量。
